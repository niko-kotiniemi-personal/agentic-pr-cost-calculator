# Changelog

Every change that an adopter of the tool would notice is listed here, newest first, in the form [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) describes. Versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html): the major number rises for a change that adopters must act on, the minor number for new behaviour, and the patch number for a fix. DR-096 (Versions are semantic) and DR-154 (The public surface is what adopters configure or depend on) define what counts as each.

A release's entry lists any breaking change under `### Breaking`, and the release workflow refuses a release that lists one without raising the major number.

## [Unreleased]

### Added

- The repository's foundations: the OpenSpec proposal for the tool, its threat model with a risk matrix, the requirements register, the feature pages, the page explaining how the tool works, and a record of each decision.
- The assumptions that the tool's design rests on, in `docs/assumptions/`: what each one holds up, what would change if it were wrong, and how each of its facts is checked, with those about adopters' own setups among them.
- A glossary, `docs/glossary.md`, giving each word that the pages use its meaning and the words to avoid for it, with a test that fails on a word to avoid in a page's prose, and the pages reworded to its terms.
- The proposal's privacy design: consent that holds for each recorded call, a local store for each user that keeps ids only as hashes, readable by its owner alone except on Windows, and for no longer than 30 days, and a ledger format that states its version on each file's first line and is published with a JSON Schema.
- The proposal's rule that a `.pr-cost.json` that holds a key the tool does not know, gives a key twice or has no `enabled` of `true` or `false` is not valid and leaves the tool off, so that a misspelt key is not passed over, and that the report says when a merge leaves the tool off.
- The proposal's plugin: the capture step also comes as a Claude Code plugin, so that a project's cloud threads, which run no repository's hooks, are recorded too. A person installs it from each release's zip, whose checksum the README gives, or from this repository as a marketplace that serves only a published release's plugin, and in a cloud environment opts in with one line in the environment's setup script, which an organization can also put in an environment that it shares with its members. Each ledger file names the release that wrote it, so that the comment says when a person's plugin is of a later release than the repository's report, each release is published only once its zip and its bill of materials are attached and checked, and the README says how to turn capture off in a session that is running.
- The proposal's rule for line endings: the registered command and the plugin's command take each CRLF as LF before they compare the capture step with the checksum that they carry, so that a checkout that writes Windows line endings still runs the step, while any other change to it runs none of it.
- The proposal's rule that a run of the plugin, outside the repository that holds the project directory, starts a git command that can start a program that a repository's configuration names only where the session runs git, or to take back a ledger file that the session staged there, so that a clone that a session only meets or moves into has git start none of the programs that its own configuration names, such as `core.fsmonitor` or `gpg.program`.
- The proposal's rule that every version of the ledger format states its version and the release that wrote it on the first line in the same place and form, so that the comment says when a ledger file comes from a later release than the report's, whatever its format.
- The proposal's rule that a copy of the capture step that leaves a session to a later release's copy still acts on an opt-out that it finds, so that turning capture off is acted on once the later copy no longer runs.
- The proposal's README opening: a short start of at most 200 words outside code that says how a repository, a person and an organization turn the tool and capture on and how to stop, and, before any step that opts anyone in, what an opt-in records and publishes, with the detail folded below it under headings that show, addresses only in this repository or on its test's list, and a calling workflow whose pin is left for the commit that a published release names, and sections that tell an agent that sets the tool up to opt no one in.
- The proposal's rule that the comment says when the hook's registration does not run the repository's hook file, as when it was copied from another release's README, so that a repository whose sessions record nothing through it is told.
- The roadmap, `docs/roadmap.md`, which the README links: what is now, next and later, with the known limitations that an adopter notices, while each feature page lists the rest of its own, so that every risk of the design is listed somewhere, and `tests/test_roadmap.py`, which fails when a risk is listed nowhere, or the page links elsewhere than this repository or holds text that GitHub hides.
- Planned work kept as backlog items in `docs/backlog/`, one file each with its status, the date it last changed, a brief and what it rests on, and the roadmap made their index, so that the plan and the reasons behind each item are in the repository, with `tests/test_backlog.py`, which fails when an item is out of form, rests on what does not exist or no longer holds, or differs from its line on the roadmap; an item becomes planned only through a pull request that the owner merges. The README's section on working on this repository opens with a briefing for developers on how work flows from an issue to a merged pull request.
- The guide, `docs/patterns.md`, which the README links and `CLAUDE.md` names: how the project builds, concern by concern, each entry a principle with the pattern that it follows, the anti-patterns that it steers clear of, what holds it and where the project stands, followed, designed, knowingly accepted or a gap naming the backlog item that closes it; it steers below the specs and `CLAUDE.md`, as the default branch holds it, with the tests that hold its form and what it says of where the project stands.
- The proposal's rule that a release's guide was read for that release, and that its changelog entry names the backlog item of each gap that the guide gives under Security, Privacy, Identity and credentials, or Supply chain and releases, so that adopters of a release are told of each such gap.
- The proposal's rule, as the owner chose, that one opt-in records every agent that the tool records, each agent that a later release adds among them, which the README's short start says before any step that opts anyone in, its section on the opt-in and the opt-in's feature page say with the name of each agent recorded, and an organization tells its members; and the surface manifest's list of the agents that the opt-in records, so that the release that adds one is a major release.
