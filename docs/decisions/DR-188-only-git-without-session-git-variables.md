# DR-188: The hook starts only git, by absolute path, from a safe folder, without the session's git variables

- **Type:** security and privacy
- **Status:** accepted
- **Decided by:** the change `add-pr-cost-calculator`, as the owner asked on 2026-11-02
- **Requirements:** R54, R118, R147, R160, R169
- **Threats:** T2, T46, T119, T121, T122
- **Replaces:** DR-059
- **Closed by:** none

## Context

Hooks run in Claude's current directory, which is usually in the repository, and on Windows a program started by a name alone is looked for in the current directory before the system's folders and those that `PATH` names (see the design's context). So a `git.exe` in a folder that Claude has moved into, such as an extracted archive or a third-party clone, would run at the next git command or turn end, even for people who never opted in (T46). Python's isolated mode covers only what Python imports (T15). DR-059 decided where the hook finds git and from where it starts it, and two gaps remained. A tool that sets up a folder's environment can add an absolute entry of `PATH` that names a folder inside the repository, where a program is the repository's. And a repository's `.claude/settings.json`, or a `.claude/settings.local.json` that it tracks, can set environment variables for everyone who works in it, which reach the hook and every git command that it starts: `GIT_DIR`, `GIT_WORK_TREE` and `GIT_INDEX_FILE` choose the repository and the index that git works on, and `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_NOSYSTEM` the configuration files that it reads, so they could move the store or a staged ledger file into another repository, or keep git's reading of the opt-in from a file that turns capture off (T119). The owner asked on 2026-11-02 for a conservative boundary of consent, and that no call be attributed where that could publish another repository's usage. A review of the change's later commits, in a context separate from the one that wrote them, found two more gaps. A submodule's checkout, and a working tree whose git folder was moved out of it, have a `.git` file whose git folder holds no `commondir` file, since it is the git common directory itself. And git matches a condition that names a folder through a symbolic link only where `PWD` names, through that link, the top level of the main worktree that git runs in, so the `PWD` that a session passes on could make the hook's reading of the opt-in differ from the one that a person checks (T121).

## Decision

The hook starts no program other than git. It looks for git only in the folders that the absolute entries of `PATH` name, skipping any that lies inside this repository's working trees or its git common directory, which it learns, before it starts any program, from the project directory's `.git`, the `commondir` file in the git folder that it names, which is the git common directory itself when it holds no such file, and the `gitdir` file of each linked worktree, each opened only when it is a regular file, taking the main worktree, from a linked one, to be the folder that holds a common directory named `.git`, as `git worktree list` does, and it starts no program when it cannot read one of them, finds a folder in `worktrees/` with no `gitdir` file, or runs in a linked worktree whose common directory has another name, as a submodule's has, and a bare repository's in a folder such as `repo.git`. It starts git by that absolute path from a current directory that only the system's administrator can write, such as `/` or Windows' system folder, naming the folder that each git command works in with `-C`, and with every variable whose name begins with `GIT_` removed from the command's environment, but those that it sets itself, save for the one reading of the opt-in that DR-183 runs in the session's own environment, and with `PWD` removed from every other command's environment.

## Alternatives

- Removing only the variables that choose the repository, the working tree and the index, which would leave the configuration variables free to hide an opt-out, and would need the list kept up as git adds variables.
- Keeping the session's environment, as DR-059 did, which lets a repository's settings move the store or a staged ledger file into another repository.
- Removing `PWD` from git's reading of the opt-in in the session's environment too, which would leave only the session's `GIT_` variables to make the hook's reading find more than the command that the opt-in's pages give, but would drop an opt-out that git finds in the session's environment only through its `PWD`, against the conservative boundary of consent that the owner asked for.
- Reading the git common directory's `config`, for a submodule's `core.worktree` or a bare repository's `core.bare`, which would let capture run in a submodule's linked worktrees and in a bare repository's worktrees, which have no main worktree, but would have the hook read git's configuration format itself, a copy of git's rules that can drift from them, while a linked worktree of a repository whose git folder was moved out of its working tree to a folder of another name would still stop it, since no file in that git folder names the main worktree. The owner chose on 2026-11-04 that a bare repository's worktrees record nothing, as the usage-capture page says.

## Consequences

- A program named `git` that is planted in Claude's current directory, in the repository's folder, in a folder that a relative entry of `PATH` names, or in a folder of the repository's, or of a linked worktree outside its folder, that an absolute entry names, is never the one started (R54), and task 2.3 plants one in each on a Windows runner.
- The session's environment can neither move a call into this repository, nor move the store or a staged ledger file into another one, nor stop git from finding this repository (R169).
- A person's own `GIT_` variables reach only git's first reading of the opt-in, where they can turn capture off and never on (DR-183).
- A `safe.directory` setting that only the session's `GIT_` variables give, through `GIT_CONFIG_COUNT` or in the file that `GIT_CONFIG_GLOBAL` names, does not make git trust a clone that another user owns, so capture records nothing there until the person's global configuration, or the system's, names it (T122).
- A run that finds capture off still starts git, by the same absolute path, to find its store and to take back and put back ledger files, which T46's residual accepts (R118).
- A run that cannot read the files that list the repository's worktrees, or that finds a folder in `worktrees/` with no `gitdir` file, which git passes over, records nothing until it can, and says so on standard error, while a submodule's checkout and a working tree whose git folder was moved out of it are recorded as any other. A linked worktree whose git common directory is not named `.git` records nothing, and says so: a submodule's, or one of a working tree whose git folder was moved to a folder of another name, since the hook cannot tell where its main worktree is, and each worktree of a bare repository in a folder such as `repo.git` or `.bare`, since the hook cannot tell that it has none, so a person who keeps a bare clone with a worktree for each branch has no capture there (R54).
- The reading of the opt-in without the session's variables finds what git finds from the folder's real path, which the command that the opt-in's pages give shows when it is run from there, while a folder's opt-out whose condition names the folder through a symbolic link holds only where the `PWD` that reaches the hook names, through that link, the top level of the repository's main worktree, so the pages say to name the folder's real path (R160, R169, T121).

## Scope

This covers which programs the hook starts, from where, and with what environment. A Python module planted beside the hook is kept out by DR-125 (The hook runs in Python's isolated mode), what the git commands that the hook starts may reach over the network is DR-060 (The hook opens no network connection), and how git's reading of the opt-in is taken is DR-183 (The opt-in is read only from the person's global git configuration, and git's own reading of it can only turn capture off).

## What reversing it would change

R54 and R169 in `usage-capture` would change, with their scenarios "A program planted in the current directory is not run", "A git in a folder of the repository is not run", "A git in a worktree outside the repository's folder is not run", "A checkout whose git folder holds no `commondir` file is recorded", "A run that cannot read the files that name the worktrees starts no program", "A run in a linked worktree whose main worktree it cannot tell starts no program", "The environment cannot move the store or a staged ledger file into another repository" and "Only git's reading of the opt-in in the session's environment keeps its `PWD`", and so would R118, whose scenario "A run that finds a switch off starts git only for its store" holds that every program such a run starts is git, R147's scenario "A `safe.directory` setting that only the session's environment gives does not make the clone trusted", R160's scenario "An opt-out that git finds through the session's `PWD` turns capture off" in `switch-and-opt-in`, the design's decisions 1 and 6, T2's, T46's, T121's and T122's answers, T119, the usage-capture and opt-in feature pages, `docs/how-it-works.md` and the README's section that task 4.4 writes, and tasks 2.1, 2.3 and 2.4, which build and test the lookup and the environment.
