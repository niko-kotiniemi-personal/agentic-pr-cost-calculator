# Usage capture

While a Claude Code session works in the repository, a hook records what each model call spent, and the agent's own commits carry it to the pull request in ledger files. Nothing is sent anywhere: what the hook records stays on the machine until a commit takes it.

**Status:** designed, not built yet.

**Spec:** `usage-capture`

**Requirements:** R2, R75, R41, R42, R43, R44, R165, R45, R167, R111, R3, R147, R76, R5, R7, R148, R78, R46, R47, R8, R79, R80, R81, R82, R83, R84, R85, R86, R48, R112, R49, R50, R51, R9, R87, R52, R113, R114, R115, R116, R117, R11, R12, R53, R54, R169, R118, R13, R88, R89, R90, R55, R149, R170, R150, R151, R152, R153, R154, R155

## Expected behaviour

- **What is recorded.** For each model call, once: its UTC day, its model, a hash of its message id, whether the main agent or a subagent made it, and its input, output, cache-write and cache-read tokens. Where the transcript gives them, it also records the attributes that change the price: service tier, speed, inference region and server-side tool requests. A call is recorded only when it was made while both switches were on, as the [opt-in's page](switch-and-opt-in.md) says.
- **Placed by the line it answers.** A run reads again, from the earliest line that a call not yet recorded may still answer, the lines that earlier runs read, so that a call is placed inside or outside an interval by the line it answers, whichever run read that line. A call whose answered line comes before where runs read again, or was skipped as too long for a run's time budget, is left out, and the next ledger file staged for its worktree and branch says that calls were left out for consent, with no count.
- **Where from.** A call's repository and worktree are told by the working directory that its transcript line gives, alone, as git finds them from that directory when a run reads the call: not by what the call reads or writes, not by the branch, and not by the session's variables, such as `GIT_DIR`, that tell git which repository to use, since the git commands that tell them run without the session's `GIT_` variables. Only the calls made in the repository that holds the session's project directory, or in one of its worktrees, are recorded there. That rule has limits:
  - A call made here that works on another repository, through an absolute path, `git -C` or a `cd` inside a command, is recorded here, and a call made in another repository that works on this one is not. So work on other repositories, private ones above all, belongs in sessions of its own.
  - A repository nested inside this one's folder is not this one, and neither is a folder that contains it, so the calls made from either are not recorded here, and a session should start in the repository.
  - A call whose line gives no working directory, or whose directory is gone or names no repository that git can tell by the time a run reads it, as when a worktree is removed first, is left out. When the line gives no directory, or a directory inside this repository's folder, where Claude Code keeps its worktrees, the session's next ledger file here says that calls whose repository could not be told were left out, with no count. A directory outside it raises no flag, so no ledger file tells of work in another folder.
  - A run reads a call some time after it was made, at the session's next run. A path that holds another worktree or another repository by then sends the call there, so a run comes before and after every git command that the hook's condition matches, to keep that gap short.
- **Which branch.** A call goes to the branch checked out in its worktree when a run records it, not when it was made (DR-012). A run before every git command that the hook's condition matches records the calls that are over by then, before that command can change the branch, so a call reaches another branch only when it is the call that runs that command and its run cannot yet read it as over, when that run's time budget leaves it unread, or when the branch changes in a way that the condition does not match, as the design's risks list.
- **The store.** Between runs, capture keeps its notes in a store: one file for each user, in a folder of that user's own, `pr-cost-<uid>/store.json` in the repository's git common directory where the system numbers users, as POSIX systems do, and `pr-cost/store.json` where it does not, outside the working tree, shared by every worktree and never committed. It holds only what capture needs to tell a call's worktree and branch, to record each call once and to take back the ledger file of a command that never committed: for each session, its intervals and how far each transcript was read; each waiting call's entry and each flag due, with the worktree and branch they go to; the day of each call that a commit took; and, until a run resolves it, a note of each staged or taken-back ledger file. A session's id, a transcript's path, a worktree, a branch, a `tool_use_id` and a call are held as SHA-256 hashes, and the fingerprint of the files that hold the opt-in as a hash too, with no path. The only plain names are a staged ledger file's path, its worktree's name and its transcript's path, which carries the session's id, and a taken-back one's path and worktree's name, which go when their note does. None of these ids, paths and names reaches a ledger file, and the store never leaves the git common directory.
- **For 30 days at most.** The store's retention window is 30 days. A run records no call whose day is more than 30 days before its own, and drops a waiting call, a flag due or a taken call's note that old, and the next ledger file staged for a dropped waiting call's worktree and branch says that calls were left out for their age, with no count. A session's notes go once none of its runs has come within the window, a ledger file staged that long ago is taken back as for a command that is over, and a store that holds nothing removes itself. Retention runs at every run that finds a store of a version that it knows, whatever the switches say, and only then, so a repository where no session runs again keeps its store until the person removes it.
- **For its owner alone.** Each user's store is in a folder of that user's own. Each write leaves the store's folder readable, writable and enterable by its owner alone, mode 0700, and its file readable and writable by its owner alone, mode 0600, whatever the umask, writing a new file and renaming it over the old one, never through a link. A run leaves alone a store whose file or folder is a link, or on Windows another reparse point, is not a regular file or a folder, or belongs to another user, and acts on a note only for a ledger file of the form that it writes, in a worktree of this repository. A run that cannot make its store's folder records nothing. On Windows, the step checks neither the store's access list nor its owner, so there the store has the access of the git common directory around it.
- **A removed store.** A store that the person removes, or that does not parse, as when a sync or a power loss cut it short, takes its notes with it: no call that answers a line written before the next run that finds both switches on is recorded, and a ledger file staged before the removal is left to git. A run that finds a switch off removes a store that does not parse, and one that finds both on replaces it. A store does not parse only when a run cannot read a version from it, or reads one that it knows from a store that is not of that version's form, so a run never takes for a broken one a store that it leaves alone above, or one that a later release wrote. So before removing the store, look for a staged ledger file with `git status` in every worktree that `git worktree list` names. A session resumed in a fresh clone at the same path, which holds no store, records none of the calls that answer a line written before its first run there.
- **A clone that git does not trust.** git refuses to work in a repository whose folder another user owns, unless a `safe.directory` setting names it, so capture records nothing there, with no flag, until one in the person's global configuration, or the system's, does. Capture runs git without the session's `GIT_` variables, so a setting that only they give does not count. Adding one to the person's global configuration ends every open interval in their other repositories, as any write to it does.
- **Worktrees that capture leaves out.** Before it starts any program, capture reads the project directory's `.git`, the `commondir` file of the git folder that it names and each linked worktree's `gitdir` file itself, to learn which folders hold the repository's working trees, so that it never starts a git that one of them holds. A run that cannot read one of them, finds a folder in `worktrees/` with no `gitdir` file, or runs in a linked worktree whose git common directory is not named `.git` records nothing, and says so on standard error. So capture records nothing in a submodule's linked worktrees, in a linked worktree of a repository whose git folder was moved to a folder of another name, or in any worktree of a bare repository in a folder such as `repo.git` or `.bare`, as when a person keeps a bare clone with a worktree for each branch (DR-188).
- **No transcript kept.** Capture writes no line of a transcript, and no value from one beyond an entry's fields and the store's notes, to any file or to standard error. A pull request's cost is recomputed from its ledger, the price table and GitHub's jobs API alone, and keeping or reprocessing transcripts would need a change of its own (DR-178).
- **When.** The hook runs when a session starts, is resumed or forked, or is cleared or compacted; when Claude finishes responding, when a subagent finishes, when a turn ends in an API error and when the session ends; and before and after each of the agent's Bash commands that the hook's condition `Bash(git *)` matches. The run when a session starts, a start run, reads no transcript: it takes back and puts back what is due, as any run does, and begins the session's interval when it finds both switches on and no store whose version it does not know.
- **How it reaches the pull request.** Just before the agent's `git commit`, the hook writes the waiting calls of that commit's worktree and branch into one new ledger file, with the flags due there, and stages it, so that the commit takes it. It does this only for a commit whose branch and contents it can tell from the command. Otherwise the calls wait for a later commit.
- **When no commit takes the file.** If the commit fails, is refused at a permission prompt or by a permission rule, is cancelled or never runs, the hook takes the file back, and its calls and flags wait for a later commit.
- **Removed calls stay removed.** Once a run has found a commit holding a ledger file, the hook never stages that file's calls again in that clone, so a ledger file removed after that takes its calls with it.
- **Counts are checked.** A call with a count that is not a whole number within the documented ceiling is refused, and the ledger says how many calls were refused.
- **Two runs at once.** Runs at the same time, such as the main agent's and a subagent's, never split each other's notes or record one call twice.
- **It never gets in the way.** A failure in the hook never stops the session. The hook prints nothing that Claude reads, writes no transcript text anywhere, and stops at a time budget, leaving the rest for its next run.

## Not covered

- Commits the hook cannot follow: `git merge`, `git cherry-pick`, `git rebase --continue`, a script, an API, a commit in the background, in a pipeline, a subshell or a group, joined by `||` or behind a wrapper, and commits made through Claude Code's PowerShell tool. Their calls wait, and may reach no pull request. The design's risks list every such case.
- Agents other than Claude Code.

## How it is validated

This feature is validated first by its spec's scenarios: each gets an acceptance test before its code, seen to fail for the expected reason (task 1.4). Then come the checks that DR-084 to DR-093 and DR-109 apply to all the tool's code. Beyond those, this feature has its own:

- Synthetic transcripts and hook inputs in each shape that Claude Code writes, with the lines for commands refused at a permission prompt or by a permission rule, and for blocked, cancelled and interrupted ones, checked against what Claude Code writes for them, and with calls made in another repository, in a repository nested in this one, in its worktrees and with no working directory, and calls that work on another repository through an absolute path or a `cd` inside a command (task 1.1).
- The store's format, field by field, with each field's purpose and how long it is kept, the retention window and the store's modes, written down before the code, with the tests reading those values from it (task 1.2).
- Unit tests at every boundary of the counts, and property tests that no planted string reaches the ledger or any file but the store's note of a staged ledger file, and that a second run changes nothing (task 2.1).
- Tests of the store: that it holds ids and paths only as hashes while no file is staged, keeps a staged file's names only until a run resolves it, keeps nothing past its retention window and flags the waiting calls it drops, removes itself once it holds nothing, is left for its owner alone at each write, is left alone when it is a link, another user's or of a version that the run does not know, and is treated as removed when it does not parse (task 2.1).
- Tests against real git of the commits that the hook follows and of those it does not, those refused at a permission prompt or by a permission rule, cancelled or interrupted included (task 2.2).
- What the README's section on adopting the tool says about how git treats a ledger file, tested with the CI runner's git and, in a CI job of its own, with git 2.43 (task 4.4).
- The hook run from another directory and in each shell that its registered command meets, Windows PowerShell included, and a start run that reads no transcript and prints nothing (task 2.3).
