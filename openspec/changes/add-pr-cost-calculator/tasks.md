# Tasks

Design decision 8 is how every task below is verified. Each task's acceptance tests are written in group 1, before any code.

## 1. Verification first, before any code

- [ ] 1.1 Write synthetic transcript and hook-input fixtures covering a plain reply, each tool type, an MCP call, both shapes of subagent transcript (earlier lines with partial usage, and calls whose lines give no stop reason and lack the fields that final lines carry, among them the server-side tool requests), a call written over several lines, a call still being written, final lines of one call that disagree, calls made in another repository, in a folder above this one, in a repository nested inside it and in one of its worktrees, a call that works on another repository through an absolute path, a detached HEAD, a session resumed in a fresh clone, repeated runs, an unknown tool, model names and attribute values that the price table does not list, Bash commands that do and do not run `git commit` here, among them `git add` and `git commit` in one command, a commit after another command, a commit in the background, and commits that are refused, blocked by another hook or cancelled, a run while Claude's current directory is in another repository, a symbolic link and an oversized file in the branch's ledger folder, and hostile strings and values, each hostile fixture named for it; and verify that no fixture holds real data, and that the lines the fixtures give for a refused, blocked or cancelled command have the shape that Claude Code writes for them
- [ ] 1.2 Document the ledger format in `docs/ledger-format.md`: the entry, the counts of refused calls and of calls read without a stop reason, the names an entry may hold, which are those the price table lists and `unknown`, the count ceiling, the size bound and the opt-in setting; and verify that the tests read those values from it
- [ ] 1.3 Add the traceability test, and verify it fails now, naming every scenario that has no test
- [ ] 1.4 Write the acceptance tests for every scenario in `usage-capture`, `cost-pricing` and `cost-reporting`, as expected failures that may not pass early, and verify that each fails for its expected reason and that 1.3 then passes
- [ ] 1.5 Add 100% branch coverage and mutation testing as CI gates, and verify that each fails on a planted uncovered branch and on a planted surviving mutant
- [ ] 1.6 Add the network guard and a derandomised Hypothesis profile for CI, and verify that a test opening a connection fails
- [ ] 1.7 Run every shell script through shellcheck and check that every CI job is gated by the aggregate `ci` job, and verify that each check fails on a planted violation and reports what it examined
- [ ] 1.8 Lock every development dependency, including the tools' own dependencies, with hashes, and install them with `--require-hashes` in CI and in sessions; verify that an install fails on a planted wrong hash and on an unlisted package
- [ ] 1.9 Extend the private-reference check to the messages and files of every commit a pull request adds, with CI fetching the pull request's base commit for it, and verify that it fails on a planted reference in a commit message and in a file that a later commit of the same pull request removes

## 2. Usage capture (`usage-capture`)

- [ ] 2.1 Implement the transcript reader and the store in the common git directory: this repository found from the project directory, a run before and after every git command as well as when an agent stops, reading on from the last run within a time budget, the working-directory filter by git common directory, calls read from their lines that give a stop reason or, once over, from their last line and counted, subagent transcripts, each call's worktree and branch or the lack of one, model names and attribute values checked against the price table the hook ships with, the branch's ledger files read as git blobs, skipping what is not a regular file or is above the size bound, and refused calls; and verify that their acceptance tests pass, with unit tests at every boundary and property tests that no planted string reaches the ledger and that a second run changes nothing
- [ ] 2.2 Implement writing a ledger file around a commit: recognising a command that runs `git commit` in this repository, staging only for a commit in the foreground that nothing but changes of directory and the git commands `add`, `rm`, `mv`, `status`, `diff`, `log` and `show` come before, one new file with a random name, created only if absent, the symbolic-link refusal, staging that file alone and despite ignore rules, writing nothing for a commit that names its paths, or that would otherwise be empty when nothing before it stages files, taking back a file that no commit took, in the command's own run after it ends or, for a command that gets no such run, in the next run, never removing a file that a commit holds, leaving the file while another git command holds the index, and whole records when runs overlap; and verify that their acceptance tests pass against a planted link, a working tree with other changes, an ignore rule, a failed commit, a commit that is refused, blocked, cancelled or moved to the background, `git add` and `git commit` in one command, a commit after another command, a held index lock, commands that only name a commit, and two runs at once
- [ ] 2.3 Add the hook script, as one file that imports only the standard library, and its registration for `Stop`, `SubagentStop` and `StopFailure`, and for `PreToolUse`, `PostToolUse` and `PostToolUseFailure` on Bash with the condition `Bash(git *)`, as `python3 -I "${CLAUDE_PROJECT_DIR}/<script>" || true` with a timeout, documented in the README; verify that a hook run against a fixture leaves the expected ledger, also when it runs from another directory, that a test holds the isolated mode, the project directory, the `|| true`, the condition and the timeout, that the file runs from a folder that holds nothing else but a planted `json.py` without importing it, and that the registered command exits with success and prints nothing on standard output when its script is missing or unreadable
- [ ] 2.4 Read the per-person opt-in from the global configuration files in the home directory only, not from files they include, ignoring the environment variables that point git at other configuration or add settings, and let the repository's own git configuration turn capture off but not on; and verify that capture stays off when only the repository's own git configuration turns it on, when `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_COUNT` or `GIT_CONFIG_PARAMETERS` turns it on, when only an included file turns it on, and when the repository's own configuration turns it off

## 3. Pricing (`cost-pricing`)

- [ ] 3.1 Add `prices/models.json` and `prices/github-actions.json` with each row's effective date and source, including the price modifiers, web fetches at no charge, and how modifiers combine, and verify that a test checks every row has both, and fails when a pull request changes or removes an existing row, or adds one dated on or before the newest existing row for the same price, with CI fetching the pull request's base commit for it
- [ ] 3.2 Implement token pricing, the price modifiers and their combinations as the price table states them, the cache-lifetime range, entries dated before any price or after the report's day, and unpriced models and attributes; and verify that their acceptance tests pass, with property tests that a cost is never negative and adds up across any split of the ledger
- [ ] 3.3 Implement CI minutes from job times, with per-job rounding, every attempt of every job, the pull request's own commits read from git through `refs/pull/<number>/head` whatever the merge method, only the runs created before the merge, so that the merge's own runs are left out, jobs on runners that the price table does not list counted in minutes and left out of the cost, and listings that are incomplete or not finished; and verify that their acceptance tests pass against recorded API responses, for a merge commit, a squash, a rebase merge and a fast-forward

## 4. Reporting (`cost-reporting`)

- [ ] 4.1 Implement reading the configuration from the default branch before and after the merge, flagging a changed configuration or workflow file, refusing a push whose commits do not all belong to one pull request, the comment with its counts of refused calls and of calls read without a stop reason, and the lower bound that the second count makes the token cost, its update of only its own comment, and only names that the price table lists in the comment; and verify that their acceptance tests pass, with a property test that no planted string reaches the comment
- [ ] 4.2 Implement reading ledger files as git blobs: refusing paths that are not regular files, learning sizes before reading, counting only the files the merge adds, skipping calls the default branch held before the merge, counting a repeated call once and refusing entries of one call that differ, and flagging removed or changed ledger files; and verify that their acceptance tests pass
- [ ] 4.3 Add the reusable workflow, which refuses every event but a push to the default branch, checks out its own code by `job.workflow_repository` at `job.workflow_sha` without keeping the token, and declares only `contents: read`, `actions: read` and `pull-requests: write`; let the repository's workflow tests allow exactly those permissions for this workflow alone, and a local reference to it; and verify with tests that hold each of these
- [ ] 4.4 Write the README's section on adopting the tool: the calling workflow, pinned to a full commit, granting only the permissions in 4.3 and passing no secrets; copying the hook file from the full commit that the calling workflow pins and checking its checksum, and updating the two together; the hook registration; each person's opt-in, and turning it off in one repository; that a session should start in the repository, and that any work it does on other repositories from there, private ones included, is recorded too; what a public repository publishes when the tool is on; the calls that reach no commit, as the design's risks list them; that CI runs on commits that a force-push removed are not counted; and that a pull request based on one that was merged by squashing or rebasing counts that one's runs again unless it is rebased first; and verify with a test that parses the calling workflow in the README and holds its trigger, its pin, its permissions and the absence of secrets
