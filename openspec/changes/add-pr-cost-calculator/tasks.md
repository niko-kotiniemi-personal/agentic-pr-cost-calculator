# Tasks

Design decision 8 is how every task below is verified. Each task's acceptance tests are written in group 1, before any code.

## 1. Verification first, before any code

- [ ] 1.1 Write synthetic transcript fixtures covering a plain reply, each tool type, an MCP call, both shapes of subagent transcript (earlier lines with partial usage, and calls whose lines give no stop reason, one of them with only partial usage), a call written over several lines, a call still being written, final lines of one call that disagree, calls made in another repository, in a folder above this one, in a repository nested inside it and in one of its worktrees, a call that works on another repository through an absolute path, a detached HEAD, a session resumed in a fresh clone, repeated runs, an unknown tool, model names and attribute values that the price table does not list, Bash commands that do and do not run `git commit` here, and hostile strings and values, each hostile fixture named for it; and verify that no fixture holds real data
- [ ] 1.2 Document the ledger format in `docs/ledger-format.md`: the entry, the counts of refused calls and of calls read without a stop reason, the name pattern, the count ceiling, the size bound and the opt-in setting; and verify that the tests read those values from it
- [ ] 1.3 Add the traceability test, and verify it fails now, naming every scenario that has no test
- [ ] 1.4 Write the acceptance tests for every scenario in `usage-capture`, `cost-pricing` and `cost-reporting`, as expected failures that may not pass early, and verify that each fails for its expected reason and that 1.3 then passes
- [ ] 1.5 Add 100% branch coverage and mutation testing as CI gates, and verify that each fails on a planted uncovered branch and on a planted surviving mutant
- [ ] 1.6 Add the network guard and a derandomised Hypothesis profile for CI, and verify that a test opening a connection fails
- [ ] 1.7 Run every shell script through shellcheck and check that every CI job is gated by the aggregate `ci` job, and verify that each check fails on a planted violation and reports what it examined
- [ ] 1.8 Lock every development dependency, including the tools' own dependencies, with hashes, and install them with `--require-hashes` in CI and in sessions; verify that an install fails on a planted wrong hash and on an unlisted package
- [ ] 1.9 Extend the private-reference check to the messages and files of every commit a pull request adds, with CI fetching the pull request's base commit for it, and verify that it fails on a planted reference in a commit message and in a file that a later commit of the same pull request removes

## 2. Usage capture (`usage-capture`)

- [ ] 2.1 Implement the transcript reader and the store in the common git directory: reading on from the last run within a time budget, the working-directory filter by git common directory, calls read from their lines that give a stop reason or, once over, from their last line and counted, subagent transcripts, each call's worktree and branch or the lack of one, model names and attribute values checked against the price table the hook ships with, and refused calls; and verify that their acceptance tests pass, with unit tests at every boundary and property tests that no planted string reaches the ledger and that a second run changes nothing
- [ ] 2.2 Implement writing a ledger file around a commit: recognising a command that runs `git commit` in this repository, one new file with a random name, created only if absent, the symbolic-link refusal, staging that file alone and despite ignore rules, writing nothing for a commit that would otherwise be empty or that names its paths, taking back, in the command's own run after it ends, a file that no commit took, and whole records when runs overlap; and verify that their acceptance tests pass against a planted link, a working tree with other changes, an ignore rule, a failed commit, commands that only name a commit, and two runs at once
- [ ] 2.3 Add the hook script, as one file that imports only the standard library, and its registration for `Stop`, `SubagentStop` and `StopFailure`, and for `PreToolUse`, `PostToolUse` and `PostToolUseFailure` on Bash with the condition `Bash(git *)`, as `python3 -I <script> || true` with a timeout, documented in the README; verify that a hook run against a fixture leaves the expected ledger, that a test holds the isolated mode, the `|| true`, the condition and the timeout, that the file runs alone from an empty folder, and that the registered command exits with success and prints nothing on standard output when its script is missing or unreadable
- [ ] 2.4 Read the per-person opt-in from the global configuration files in the home directory only, ignoring the environment variables that point git at other configuration or add settings, and let the repository's own git configuration turn capture off but not on; and verify that capture stays off when only the repository's own git configuration turns it on, when the environment points git at a file that turns it on, and when the repository's own configuration turns it off

## 3. Pricing (`cost-pricing`)

- [ ] 3.1 Add `prices/models.json` and `prices/github-actions.json` with each row's effective date and source, including the price modifiers, web fetches at no charge, and how modifiers combine, and verify that a test checks every row has both, and fails when a pull request changes or removes an existing row, or adds one dated on or before the newest existing row for the same price, with CI fetching the pull request's base commit for it
- [ ] 3.2 Implement token pricing, the price modifiers and their combinations as the price table states them, the cache-lifetime range, entries dated before any price or after the report's day, and unpriced models and attributes; and verify that their acceptance tests pass, with property tests that a cost is never negative and adds up across any split of the ledger
- [ ] 3.3 Implement CI minutes from job times, with per-job rounding, every attempt of every job, the pull request's own commits read from git through `refs/pull/<number>/head` whatever the merge method, the merge's own runs left out, and listings that are incomplete or not finished; and verify that their acceptance tests pass against recorded API responses, for a merge commit, a squash and a rebase merge

## 4. Reporting (`cost-reporting`)

- [ ] 4.1 Implement reading the configuration from the default branch before and after the merge, flagging a changed configuration or workflow file, refusing a push that merges more than one pull request, the comment with its counts of refused calls and of calls read without a stop reason, its update of only its own comment, and the name pattern in the comment; and verify that their acceptance tests pass, with a property test that no planted string reaches the comment
- [ ] 4.2 Implement reading ledger files as git blobs: refusing paths that are not regular files, learning sizes before reading, counting only the files the merge adds, skipping calls the default branch held before the merge, counting a repeated call once and refusing entries of one call that differ, and flagging removed or changed ledger files; and verify that their acceptance tests pass
- [ ] 4.3 Add the reusable workflow, which refuses every event but a push to the default branch, checks out its own code by `job.workflow_repository` at `job.workflow_sha` without keeping the token, and declares only `contents: read`, `actions: read` and `pull-requests: write`; let the repository's workflow tests allow exactly those permissions for this workflow alone, and a local reference to it; and verify with tests that hold each of these
- [ ] 4.4 Write the README's section on adopting the tool: the calling workflow, pinned to a full commit, granting only the permissions in 4.3 and passing no secrets; copying the hook file from a release tag and checking its checksum; the hook registration; each person's opt-in, and turning it off in one repository; that a session should start in the repository, and that any work it does on other repositories, private ones included, is recorded too; what a public repository publishes when the tool is on; and that calls after the last commit, and CI runs on commits that a force-push removed, are not counted; and verify with a test that parses the calling workflow in the README and holds its trigger, its pin, its permissions and the absence of secrets

## 5. Review

- [ ] 5.1 Run `/simplify`, `/security-review`, `/code-review` and `/verify` in a context separate from the one that built the change, and verify that every finding is fixed or answered before the owner merges
- [ ] 5.2 Revisit `docs/threat-model.md` against what was built, and verify that every threat's citations still resolve and still say what holds the answer

## 6. Integration

- [ ] 6.1 Turn the tool on in this repository, with the owner's own opt-in set outside the repository, and verify that this change's own merge posts a report whose figures can be recomputed from its ledger, the price table and the jobs API, and whose CI minutes are those of the runs that GitHub lists for this pull request's own commits
