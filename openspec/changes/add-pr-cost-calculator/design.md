# Design

## Context

See `proposal.md` for why. These facts shape the approach:

- Claude Code writes each session's transcript as JSON lines on the machine running the session. Each assistant message carries its model and a `usage` block with input, output, cache-write (split into five-minute and one-hour lifetimes) and cache-read tokens. Current versions also give the service tier, the speed, the inference region and the server-side tool requests, all of which can change the price. One message can be written over several transcript lines. In the main transcripts examined, every line of a message gave its stop reason and the same usage. Subagent transcripts were seen in two shapes. In some, a message's earlier lines gave partial usage and no stop reason, and only its last line gave the final usage and the stop reason. In others, almost no message had a line that gave a stop reason, and every line of such a message lacked fields that final lines carry, among them the server-side tool requests, and gave few output tokens even for a message that called tools: the usage of the call's start, not its end.
- Each transcript line names Claude's current directory at the time of the call. Claude Code keeps a `cd` from one command to the next only while it stays within the project directory and the directories added to the session, resets it after a command that leaves them, and never keeps one for a subagent. So a call that works elsewhere through absolute paths, with `git -C`, or with a `cd` inside its command, still names the directory Claude was in. The branch a line names was seen reading `HEAD` while a branch was checked out, so it is not used.
- Claude Code runs hooks at set points of a session. `Stop` runs when the main agent finishes responding, and not when the user interrupts it. `StopFailure` runs instead when a turn ends in an API error. `SubagentStop` runs when a subagent finishes, including the agents Claude Code runs for its own features, and names the subagent's own transcript as `agent_transcript_path`. `SessionEnd` runs when a session ends, as when the person exits or runs `/clear`, and its hooks share a budget of 1.5 seconds, which a hook's own `timeout` raises to match, up to 60 seconds. `PreToolUse` runs before a tool call, with a Bash command's text and the call's `tool_use_id` in its input, and before any permission prompt, and it runs again for a call that a hook deferred when that call is resumed. `PostToolUse` or `PostToolUseFailure` runs after a call that ran, as it succeeded or failed. A call refused at a permission prompt or by a rule, blocked by another hook, or cancelled while it runs gets neither; Claude Code documents that a blocked call's reason comes back to Claude as the call's error, and that a cancelled call's result carries the interruption message. A command run in the background, or moved there by Claude Code when it reaches its timeout, returns its result before it ends. Claude Code documents that the transcript is written asynchronously and can lag behind the conversation, and that all matching hooks run in parallel.
- A hook on a tool event can carry an `if` condition in permission-rule syntax, such as `Bash(git *)`, which Claude Code checks against each of the commands that a Bash input is made of, those inside `$()` included, and a hook with an `if` condition on any other event never runs. The condition matches a command as Claude wrote it, once leading variable assignments and a fixed list of wrappers, such as `timeout` and `nohup`, are stripped. So git run by its path, through `sh -c`, `env` or an environment runner, or through a shell alias or function does not match it, and Claude Code applies the aliases and functions of the person's shell start-up file to every Bash command. When Claude Code cannot tell which commands an input runs, it runs the hook anyway.
- Every hook receives the transcript's path and Claude's current directory, as `cwd`. A command hook runs in that directory, with two exceptions: in a worktree session started from the desktop app it runs in the main checkout's root, and when that directory no longer exists it runs from the first that still exists of the session's start directory, the project root, the home directory and the temp directory. `CLAUDE_PROJECT_DIR` names the project root, and stays there when Claude changes directory or enters a worktree. Claude Code creates its worktrees under `.claude/worktrees/` in the repository's folder. A hook's command runs in `sh`, in Git Bash on Windows, or, on Windows without Git Bash, in PowerShell, for which Claude Code rewrites `${CLAUDE_PROJECT_DIR}` into PowerShell's own form.
- What a hook's exit code and output do, as Claude Code documents them: Claude never sees the standard error of a hook that exits 0. A `PreToolUse` hook that exits 2 blocks the tool call. A `Stop` or `SubagentStop` hook that exits 2 sends Claude back to work with the hook's standard error as the reason, unless its standard output is empty and its standard error says that a file is missing, which Claude Code treats as a non-blocking error. JSON printed on standard output can block or approve whatever the exit code, except that an exit of 2 blocks whatever the JSON says. Python exits 2 when it cannot open its script, and says that the file is missing or that permission is denied. A command hook's default timeout is 600 seconds, and a timed-out `PreToolUse` hook does not block the tool call.
- A repository's `.claude/settings.json` can set environment variables for everyone who works in it, and they reach every process Claude Code starts, its hooks included. Claude Code ignores some variables from project settings, among them `HOME` and the `XDG_*` variables. Git reads its global configuration from the file that `GIT_CONFIG_GLOBAL` names when it is set, and `GIT_CONFIG_COUNT` with its companion variables adds settings.
- A cloud session's machine is disposable, and the transcript is gone after it ends, so usage has to be captured during the session. Reading transcripts after the fact also turned out to be slow at the scale of a long pull request.
- GitHub's jobs API gives each job's start and end times with the default `GITHUB_TOKEN` and `actions: read`. It lists only the latest attempt of each job unless asked for all of them, and a job that has not finished has no end time. Its per-run "billable" timing figure was seen returning zero, so minutes are computed from job times.
- A squash merge puts one new commit on the default branch, and GitHub's rebase merge always makes new commits, so neither brings to the default branch the commits that CI ran on. A pull request's head stays readable from git as `refs/pull/<number>/head`.
- A reusable workflow receives its caller's `github` context, including the event that triggered the caller. The `job` context names the reusable workflow's own repository and commit. Events caused by `GITHUB_TOKEN`, such as a merge a workflow makes, start no new workflow run.
- Anthropic's pricing has modifiers beyond the four token rates: higher rates for long prompts on some models, a multiplier for US-only inference, premium rates for fast mode, and a charge per web search. Web fetches cost nothing beyond their tokens.

## Goals / Non-Goals

**Goals:**

- Capture with no service outside GitHub and the repository itself.
- Keep everything a public repository can publish: counts, prices and totals, never content.
- Publish a person's usage only with that person's consent, and only the calls their sessions make from the repository that publishes it.
- Make every number in a report reproducible from the ledger, the price table and the jobs API.
- Treat everything that crosses into the tool as untrusted: transcripts, ledgers, API data, and the pull request being reported. `docs/threat-model.md` lists the threats and what answers each.

**Non-Goals:**

- Billing reconciliation. The figure is an API-equivalent estimate, and plans, discounts and included minutes are not modelled.
- Agents other than Claude Code in this change. The ledger format is documented so they can be added later.
- The cost of AI code review on the pull request, such as the tokens a review app or a review job in CI spends. The owner decided on 2026-10-18 to leave it to a later change, which can add it once it is known where that usage can be read.
- Live cost while a pull request is open. The report runs at merge.
- GitHub Enterprise Server, which lacks the `job` context values that decision 7 relies on.
- Shell commands sent through Claude Code's PowerShell tool, which is on by default on Windows for claude.ai and Console accounts, always on there without Git Bash, and can be turned on elsewhere. A hook registered for Bash never runs for those commands, so capture stages nothing for a commit made through that tool and does not see a change of branch made through it. Supporting them would take a second parser, for PowerShell's syntax. The hooks that run whatever the tool, when a turn, a subagent or a session ends, still run on Windows without Git Bash, in PowerShell, so the registered command is written to exit with success there too (decision 1).

## Decisions

### 1. Capture with Claude Code hooks, into the git directory, then into the agent's own commits

One script is registered for seven hook events: `Stop`, `SubagentStop`, `StopFailure` and `SessionEnd`, and `PreToolUse`, `PostToolUse` and `PostToolUseFailure` for Bash commands, with the condition `Bash(git *)`, so that around Bash commands it starts for those that run git as Claude writes it, and for any whose commands Claude Code cannot tell (see Context).

This repository is the one that holds `CLAUDE_PROJECT_DIR`, so a run means the same repository whatever directory Claude has moved to. Every run, whether a turn, a subagent, a failed turn or the session has ended or a git command is about to run or has run, reads the session's transcript on from where it last stopped, and the subagents' own transcripts, which Claude Code keeps in a `subagents/` folder nested under the session's. It keeps each call whose line gives a working directory in this repository: one whose git common directory is this repository's, so that the repository's worktrees count and a separate repository nested in its folder does not. It records each such call in a store inside the repository's common git directory (`git rev-parse --git-common-dir`), outside the working tree and shared by every worktree, together with the worktree that git itself finds from the directory the call's line names, which for a directory inside a worktree under the repository's folder, as Claude Code's are, is that worktree and not the main checkout around it, and the branch checked out there when the call is recorded, or the fact that none was. Because a run comes before every Bash command that the condition matches, a call that the transcript holds as over by then is recorded before that command can change its branch. Apart from staging a ledger file, taking it back and putting it back, as below, it changes nothing in the working tree or the index, so recording never blocks switching branches or rebasing.

A call's usage is read from its lines that give a stop reason. Where none does, as in one shape of subagent transcript, the call is read from its last line once it is over: once a later call follows it in the same transcript, or once its agent has stopped, which `Stop`, `StopFailure` and `SubagentStop` say. The ledger counts the calls read that way, because their lines give the usage of the call's start, and the comment gives that count and says that the token cost is then a lower bound. A call that is not over yet waits for a later run.

Before a Bash command that runs `git commit` in this repository, the script first reads the transcripts as above. A command runs `git commit` when one of the commands it is made of, split as the shell splits it, is `git`, then any of git's own options, then `commit`, and is not a dry run, which it is when any of `--dry-run`, `--short`, `--porcelain`, `--long`, `-z` and `--null` is in effect once git has read the commit's options, in any spelling that git accepts, such as `--dry` or `-qz`. For git, `--short`, `--porcelain` and `--long` are one setting, which the `--no-` form of any of them clears, so `git commit --porcelain --no-short` makes a commit. A `PreToolUse` run comes before the whole command, so it cannot see what an earlier part of the command will stage, nor which branch a commit after an arbitrary command lands on, nor when a commit in the background will run. So the script stages a ledger file only when the commit is a top-level command, joined to the rest by `&&`, `;` or line breaks and not part of a pipeline, whose other commands run beside it, runs in the foreground, which a commit followed by `&` does not, and comes after nothing but `cd` to a path written in the command and the git commands `add`, `rm`, `mv`, `status`, `diff`, `log` and `show`, with or without git's own options, which are what an agent runs before a commit and which do not change the branch themselves. A command substitution or a process substitution runs before the commit, or beside it, wherever it is in the commit or in a command before it: in an argument, in a leading assignment, or in a redirection. So each counts as a command that comes before the commit, except one whose only command is `cat` reading a here-document whose delimiter is quoted, which is one way to pass a message of several lines, and in whose body the shell expands nothing. The shell runs any command substitution in the body of a here-document whose delimiter is not quoted, so when the commit or a command before it reads one, the script stages nothing. For any other command it stages nothing, and the calls wait for a later commit. The worktree where the commit runs is the hook input's `cwd`, followed through each top-level `cd` before the commit and the `-C` options given to git before `commit` in the commit's own command, never the directory the hook runs in, which in a desktop worktree session is the main checkout (see Context), and the script stages nothing when such a `-C` option names a path that is not written in the command. A `-C` given to an earlier git command does not move the commit, and a `-C` after `commit` names a commit whose message the commit reuses.

When it stages, the script writes the calls recorded for that worktree and the branch now checked out there, which no ledger file on that branch holds and which the store has not noted as taken, into one new file, `.pr-cost/ledger/<YYYY-MM>/<random>.jsonl`, created only if no file of that name exists, and stages that file alone, with `--force` so that an ignore rule cannot drop it, and `--sparse` so that a sparse checkout that leaves out `.pr-cost/` cannot refuse it. It writes nothing when no call is waiting; when the command names the paths to commit, which leaves the rest of the index out; when the commit would commit nothing without the file, counting the changes to tracked files that `-a` adds, and no `git add`, `git rm` or `git mv` comes before it, so a commit that would fail still fails, and an empty commit asked for stays empty; when a `git rm` or `git mv` before the commit is given a `-C` path not written in the command, or names a path with a wildcard or other pathspec magic, a path not written in the command, or the folder that the file goes in or one above it, read from where that command runs, after the `cd`s before it and its own `-C` options, because `git rm` refuses to remove a newly staged file and fails the command, and `git mv` moves it where the script does not look for it; and when `git check-attr`, which reads every attribute file that git does, the repository's `.git/info/attributes` and the person's own among them, gives the ledger path a `filter` or a `working-tree-encoding`, because git can then commit a pointer, as Git LFS does, or the file decoded from another encoding, instead of the entries. When git refuses to add the file, as it does where `core.safecrlf` is on and line endings are converted, the script removes the file it wrote and stages nothing. When a `git add` does come first and stages nothing, the commit holds the ledger file alone instead of failing, which is a residual.

After the command, its `PostToolUse` or `PostToolUseFailure` run checks whether the commit now checked out in that worktree holds the file. If not, that run takes the file back, from the index and the working tree, and its calls wait for a later commit. Once any run finds a commit holding a file that the script staged, the store notes the file's calls as taken, and the script never stages them again in that run's clone, so that a ledger file that someone removes from the branch later, in whatever way, takes its calls with it, even when the changes of its commit are committed again. From then on the script leaves the file to git, like any file that a commit took, and never takes it back: a removal that leaves it in the working tree, untracked or with only the intent-to-add entry that `git reset -N` leaves, as a mixed `git reset` or a `git rm --cached` and a commit do, leaves it where a later `git add -A`, unless an ignore rule matches it, or for an intent-to-add entry a `git commit -a`, commits it again, with its calls, on whatever branch is checked out then, as they commit the other changes that a reset leaves. So a squash made with a mixed `git reset` and `git add -A` keeps the ledger files of the commits it squashes, and their calls, except in the cases that the risks name. A command that was refused or blocked, and so never ran, or that was cancelled or interrupted, gets no such run, and an interrupt runs no `Stop` either. So the store notes, for each staged file, the session's id, the path of its transcript, which every run of that session brings up to date because Claude Code moves a session's transcript when the session enters or leaves a worktree, and the `tool_use_id` of the command the file was staged for. Any later run of the step in the repository, from that session or another, takes the file back once it finds that command over: by the command's result in the transcript, by a later call of the agent that ran it, by that agent having stopped, or by its session having ended, which `SessionEnd` says. A run takes back and puts back what it can before it reads any transcript, as a session-end run can for every file staged for its session's commands, so that a long transcript does not use up its time first. A `PreToolUse` run that fires again for the same `tool_use_id`, as for a deferred call when it is resumed, stages nothing new while that command's file is still staged and the branch it was staged for is still checked out in that worktree. When that branch is no longer checked out there, it takes the file back first, and then, as when a run has taken the file back meanwhile, it stages anew. A take-back never removes a file from a worktree whose checked-out commit holds it, and leaves the file while another git command holds that worktree's index lock, rather than waiting for the lock or removing it. A plain `git commit` holds no index lock once it has read the index, while its `prepare-commit-msg` and `commit-msg` hooks run, so a take-back can remove the file from the index after the commit has taken it, as when Claude Code moves a commit to the background at its timeout and returns its result early. A reset in the commit's own command, as in `git commit && git reset HEAD~1`, leaves the file where that command's run takes it back, too, while a later `git reset` can go back to that commit. So every take-back notes the commit that it found checked out there, not holding the file, and whether it removed the file from the index, the working tree or both, and the first later run that finds another commit checked out in that worktree and the index free puts the file back, as that commit holds it, if that commit holds it: into the index, if the take-back removed it from there and the index lacks it, and then into the working tree, if the take-back removed it from there, the index holds it as that commit does and the working tree lacks it, before the agent's next git command could commit its deletion. Then it forgets the note, whether it put the file back or not, so that a ledger file that the person removes later, or that the step never took back, is never put back. The script puts nothing back in any other case, so that a removal that the index holds stands, as after a `git reset --soft` back to a commit that holds the file, unless it comes while a put-back is due, as the risks say. Another command can remove the file from the index in that window too, and the commit still holds it, while a take-back then finds the file only in the working tree: that removal stands as well, since the put-back into the working tree needs the index to hold the file, and the next commit deletes the file, as it would without the step. In a sparse checkout, too, the put-back puts the file into the working tree, where it would be had the step not taken it back. A put-back into the working tree puts nothing there that the index does not hold, so that a `git add` cannot stage a removed file again from it. A run that finds the index lock held leaves the note for a later run, as a take-back leaves its file. Apart from staging, taking back and putting back, no run touches the index.

A call is recorded once, by a SHA-256 hash of its message id. The store and the ids in the ledger files that the branch holds together say which calls are already recorded, so a session resumed in a fresh clone records nothing again that its branch already holds. A staged ledger file meets the repository's own git hooks, and a secret scanner can take a hash for a secret: by default, detect-secrets, a common one, flags a quoted hexadecimal string whose entropy is above a limit that SHA-256 digests exceed, unless text before it on its line names an identifier, such as a key that ends in `_id`. So the hash's field is named that way, and task 1.2 checks a ledger file against that scanner's default plugins and filters. An entry records the UTC day of the call and not its time, because pricing needs only the day, and a time on every call would show when a contributor works. An entry records whether the main agent or a subagent made the call, and no session value.

The registered command is `python3 -I "${CLAUDE_PROJECT_DIR}/<script>"; exit 0`, which finds the script whatever directory the hook runs in, with a timeout below Claude Code's default, and the script stops at a time budget inside that timeout, leaving what it has not read for its next run. Both values are set from measured run times when the hook is built. `exit 0` matters because Python exits 2 when it cannot open its script, which a `PreToolUse` hook turns into a blocked commit, and a `Stop` hook into "keep working" when the script is unreadable rather than missing. It ends the command, rather than `|| true`, because Claude Code runs the command in PowerShell on Windows without Git Bash, where Windows PowerShell 5.1 does not read `||` and there is no `true` command, while `sh`, Git Bash and PowerShell all read `;` and `exit 0`. Task 2.3 runs the command in each of those shells. The script prints nothing on standard output, and its standard error carries only its own words. Calls it refuses are counted in the ledger, because no one sees the standard error of a hook that succeeds.

The script is one file that imports only Python's standard library, because under `python3 -I` a script cannot import a module beside it, and adding its folder to the import path would undo what isolated mode is for. An adopter copies that file into their repository from the full commit that their calling workflow pins (decision 7), not from a tag, which can be moved, and checks it against the SHA-256 checksum that the README at that commit gives. The checksum shows that the copy is whole, not that the commit is honest: that rests on the choice of commit, as it does for the workflow. From then on the file is reviewed and versioned with the rest of their repository, and an update is a pull request that replaces it together with the workflow's pin. The file carries the model names and price attribute values of the price table at its commit, and records any other value as `unknown`, so that a gateway's private alias is not published. Because the hook and the report come from one commit, they share one price table, and the report refuses a name that its table does not list.

A line's working directory is Claude's current directory, not where a call worked (see Context). So a session whose current directory is in this repository, and that also works on another one, such as a private one, through paths or with a `cd` inside a command, records those calls here. No rule over a transcript's working directories can tell them apart, and telling them apart by reading what each call did would mean reading commands, which can do anything. This is a residual (the threat model's T2), and the README tells a person who opts in to keep work on other repositories out of sessions whose current directory is in a repository that has the tool on.

*Alternatives:* staging entries at the end of every turn, the first version of this design, which left the index changed between commits, so that in a test repository `git checkout` and `git rebase` refused to run; taking a ledger file that no commit took back at the next turn's end, the second version, which left it staged until then, where in a test repository it made `git rebase` refuse and followed `git checkout` to another branch, and where a run holding the index lock makes a commit fail; staging the file inside the command, by having the `PreToolUse` run rewrite it through `updatedInput`, so that a command that never runs stages nothing, which changes the command that the person and their permission rules then approve; a `pre-commit` git hook, which would sit beside the repository's own git hooks and run for every commit, not just the agent's; delivering the script as a Claude Code plugin, which a repository's own session hook can install for everyone, as this repository's hook installs Superpowers, so it would give no stronger consent than the opt-in; reading transcripts after the session through an API, which is slow and depends on access a CI job does not have; a separate service the hook posts to, which the repository would have to run and trust; pushing a separate ref from the hook, which makes every turn a network write that can fail; taking a file back at `UserPromptSubmit`, whose standard output Claude Code adds to Claude's context, and which runs only once the next prompt is sent; taking it back at `PermissionDenied`, which runs only in auto mode, where the denied command's result already lets the next run take the file back; registering the Bash hooks with no condition, which would also run around git written in forms that the condition does not match and around scripts that change the branch, but would start the script before and after every Bash command the agent runs; registering the command in exec form, which Claude Code's documentation prefers for a command that names a path placeholder, but which has no shell to turn Python's exit code 2 into success.

### 2. Python, standard library only

The hook runs on whatever machine the session uses, and the workflow runs on a stock runner. With no dependencies, both run with nothing to install, and nothing in the supply chain has to be pinned for users. Development tools (pytest, ruff, mypy, detect-secrets for task 1.2's check, and the testing tools in decision 8) are pinned in `requirements-dev.txt`, and task 1.8 locks their own dependencies too, with hashes.

### 3. The ledger is the record, and the report writes nothing to the repository

*Decided by the owner, 2026-10-18.* Using the tool means the pull request is tracked; not tracking it means not turning the tool on. Supporting both inside the tool adds complexity for no gain.

The ledger reaches the default branch with the merge and stays there. It is the pull request's record, and the cost can be recomputed from it with the price table. The report only posts its comment, so it needs no `contents: write` and no exception in a ruleset that protects the default branch.

Because a ledger file is written once, under a random name, a pull request's usage is the ledger files its merge adds. Files the default branch already held, such as those that a reused branch name still carries from an earlier pull request, are not added again, so they are not counted again. An added entry whose call the default branch already held before the merge is not counted, and a change to an earlier ledger file is flagged, not counted. A removed ledger file is not lost: git history keeps it.

*Not chosen:* a record file that could be turned off, with a workflow commit removing the ledger at merge, which needs write access and adds a commit to every pull request; keeping the ledger on a side branch that is never merged, which needs a push from the hook on every turn.

### 4. A dated price table as data in the repository

`prices/models.json` and `prices/github-actions.json` list each price with its effective date and the source page it came from, including the modifiers in the last fact under Context, and web fetches at no charge. A change to a price is a pull request that adds a row dated after the rows already there, so history is never rewritten. Anthropic publishes no price API that could replace this.

### 5. Activity type from tool names

The type comes from the first tool call in a message: edits and writes are code generation, reads and searches are file reading, shell commands are tooling, `mcp__` tools are MCP, starting a subagent is subagent, a tool the classification does not know is other, and no tool call is conversation. The rule is simple enough to test fully and to explain in one line of the report. A review cannot be told apart from other work by tool names alone, so review is not a type in this change.

### 6. The repository turns the tool on, and each person turns on their own capture

*Decided by the owner, 2026-10-18.* In a public repository, publishing someone's usage needs their own consent.

`.pr-cost.json` at the repository root holds `enabled`. Capture reads it in the working tree. The report reads it from the default branch before and after the merge (decision 7), so the pull request being reported cannot turn its own report off. A file is visible in review and versioned with the code.

Capture also needs the consent of the person whose session it records: `pr-cost.capture` set to `true` in their global git configuration. The repository decides whether the tool is used there. Only the person decides whether their session's usage is published, so an outside contributor's usage is not committed merely because the repository's owner turned the tool on.

The script reads that setting from the person's global configuration files, `~/.gitconfig` and git's file in the XDG configuration folder, not from files that they include, which can lie anywhere, a repository's folder among them, and ignores the variables that point git at other files or add settings, because a repository's settings can set those for everyone who works in it, though not `HOME` or the `XDG_*` variables. It takes the XDG folder from `XDG_CONFIG_HOME` only when that variable holds an absolute path, and reads `~/.config/git/config` otherwise, because git reads a relative one from its current directory, which can be in a repository's folder. Where both files set it, `~/.gitconfig` decides, as it does for git, which reads it after the other. One opt-in covers every repository that uses the tool, so `pr-cost.capture` set to `false` in a repository's own git configuration turns capture off there. Set to `true` there, it opts no one in.

*Not chosen:* the repository's setting alone, which would publish the usage of everyone who works in the repository, including people who never agreed to it.

### 7. The report runs on the push that a merge makes to the default branch

The tool provides a reusable workflow. A repository calls it from a workflow of its own, triggered by `push` to its default branch, which grants `contents: read`, `actions: read` and `pull-requests: write` and passes no secrets. The README gives that caller, pinned to a full commit of this tool.

A reusable workflow receives its caller's event, so the report checks the event itself and refuses anything but a push to the default branch. It checks out its own code by `job.workflow_repository` at `job.workflow_sha`, which name the reusable workflow's commit and not the caller's, and runs it with `python3 -I`, reading the caller's repository only as data.

The report finds the merged pull request with GitHub's "List pull requests associated with a commit", which for a commit on the default branch returns the merged pull request that introduced it. It looks up each commit that the push adds to the default branch's first-parent history, and when they do not all belong to one pull request, as when a merge queue merges several in one push, it posts no comment and says why in its job summary. It reads the ledger from git, comparing the push's commit before with the one after: the ledger files the merge adds, and the earlier ledger files it removes or changes. It reads `.pr-cost.json` at both commits, and runs when either turns the tool on, so the pull request that turns the tool on gets its report too.

The CI cost comes from the pull request's own commits, which the report reads from git as those that `refs/pull/<number>/head` holds and the default branch did not hold before the merge, because a squash or rebase merge brings new commits that no CI ran on. It counts only the runs on those commits that no push to the default branch started, as the event and branch that each run names show, and that were created before the pull request merged. So the runs that the merge's push starts, the report's own included, are not counted, even when they run on one of those commits, as after a fast-forward, and this does not depend on how their creation times fall around the merge time. A run that the merge starts through another event, such as a workflow on the pull request's `closed` event, is left out because it is created at the merge or after it. GitHub does not document that order, so the threat model states it as an assumption, which this repository cannot check, since none of its own workflows runs on such an event. A run counted that has not finished makes the CI cost incomplete, and a job on a runner that the price table does not list is counted in minutes and left out of the cost. Commits that a force-push removed from the pull request's head are no longer in that ref, so runs on them are not counted, and the comment says that the CI minutes are those of the pull request's own commits.

The report flags a change to `.pr-cost.json` or to any workflow file, because any workflow in the repository can run with the identity that posts the comment, and so could change it later. Because the push belongs to the base repository, a pull request from a fork gets its report too.

A pull request can still change the calling workflow itself. It can remove it, so that its own merge goes unreported, or pin a different version of the tool. Either is in its diff for review, and a pull request that changes the workflow and still gets a report has that change flagged. A merge that a workflow makes with `GITHUB_TOKEN` starts no workflow run, so it gets no report.

*Alternatives:* the `pull_request` event when a pull request closes, whose token GitHub makes read-only for pull requests from forks, so those would get no report; `pull_request_target`, which gives a write token in the base repository's context while the pull request is still untrusted, and which GitHub's documentation says to avoid when a workflow builds or runs the pull request's code; reading the configuration after the merge only, which would let a pull request turn off its own report; taking the CI commits from the push's range, the second version of this design, which after a squash or rebase merge holds none of the commits that CI ran on; GitHub's lists of a pull request's files and commits, which return at most 3000 files and 250 commits.

### 8. Everything that can be tested is tested, and every check is shown to fail

A test that passes once shows that the code can pass. It does not show that the tests would notice the code breaking. So, for every behaviour:

- **Acceptance tests come first,** at least one per scenario, each seen failing for its expected reason before its code exists. They are kept as expected failures that may not pass early (`pytest.mark.xfail` with `strict=True` and the expected error), so CI stays green and meaningful while the code is built.
- **Traceability is a test.** Every scenario has a test that names it, every test that names a scenario names one that exists, and every threat in `docs/threat-model.md` cites a scenario, task, decision or file that exists.
- **Unit tests are positive and negative,** at every boundary: zero, one, the ceiling and one above it, and the values that Python accepts where it should not, such as `true` read as a number and not-a-number read from JSON.
- **Property-based tests** (Hypothesis) hold the invariants: no planted string reaches the ledger or the comment, a second capture changes nothing, the cost adds up across any split of the ledger, and no cost is negative. CI runs them derandomised, so a run can be repeated exactly.
- **Branch coverage is 100%** of the tool's code (coverage.py). Any exclusion carries its reason.
- **Mutation testing** (mutmut) changes the tool's code one small fault at a time and expects a test to fail each time. A surviving mutant fails CI, unless it is marked as making no difference, with the reason.
- **Every check is shown to fail.** Each CI gate has a test that plants the defect it exists for, and asserts that the gate fails for that reason. Each check also reports what it examined, and fails when that is nothing.
- **No test uses the network.** A test that opens a connection fails, and recorded responses stand in for GitHub's API.
- **A defect found becomes a test** that reproduces it, before the fix.
- **End to end:** the hook runs against fixture transcripts in a temporary git repository, the report runs against a temporary repository and recorded API responses, and this change's own merge is reported (task 6.1).
- **The change is reviewed in a context separate from the one that built it,** by `/simplify`, `/security-review`, `/code-review` and `/verify`, and every finding is fixed or answered before the owner merges.

The testing tools are added to `requirements-dev.txt` with the first code, at versions that have been out for at least the 14 days Renovate waits.

*Alternatives:* one failing example per task, then green, which shows the code can pass and little more; line coverage alone, which counts the lines that ran, not the faults the tests would catch.

## Risks / Trade-offs

- [Claude Code changes its transcript format] → The parser keeps to the fields it needs, refuses unknown shapes with a count instead of guessing, and its fixtures carry every shape seen in each kind of transcript, so a change shows up as a failing test. Two final lines of one call that disagree, or a usage block whose cache-write split disagrees with its total, are refused.
- [A call read without a stop reason gives the usage of its start, not of its end] → Its output tokens and server-side tool requests are too low. The ledger counts such calls, and when there are any, the comment gives their number and says that the token cost is a lower bound.
- [Some calls reach no commit] → A call waits for a `git commit` that capture stages for, made in the worktree and on the branch where the call was recorded. So these calls are not in any pull request's ledger:
  - calls made after the agent's last such commit on a branch, such as pushing and opening the pull request, and the call that runs that commit, if that commit's run cannot yet read it as over, as it never can in a subagent transcript whose lines give no stop reason, and as it cannot when the transcript lags behind;
  - calls recorded on a branch that gets no later commit, such as the default branch before the agent branches off, or in a worktree where nobody commits, or one that Claude Code removes when a subagent finishes without changes;
  - calls recorded while no branch is checked out, as during a rebase that stops at a conflict, unless a commit is made the same way.

  Calls also wait, and may reach no commit, when the agent commits in a way that capture does not stage for: `git merge`, `git cherry-pick` or `git rebase --continue`, a script, a commit made through an API or through Claude Code's PowerShell tool, a commit in the background, in a pipeline, in a subshell or a group, joined to another command by `||`, or behind a wrapper such as `timeout`, one that follows another command in the same input, one whose message another command writes or a here-document whose delimiter is not quoted holds, or one made by git written in a form that the hook's condition does not match, as Context lists them. They wait too while a repository's own git hook refuses the ledger file, and in a repository whose attributes give the ledger path a filter or a working-tree encoding, or where git refuses to add the file, no call reaches a commit. The comment counts the usage that the pull request's commits carry, and the README says so and names these cases.
- [A call is recorded on the branch checked out when it is recorded, which can differ from the one it was made on] → A run before every Bash command that the hook's condition matches narrows this to two cases. One is the call that runs a command that changes the branch, when that command's run cannot yet read it as over. The other is calls followed by a change of branch that no command the condition matches makes: one that a script or the person makes, one made through Claude Code's PowerShell tool, or one made by git written in a form that the condition does not match, such as by its path, through `sh -c`, `env` or an environment runner, or through a shell alias or function. Those calls go to the branch checked out next. A command that the script stages for can also run a program that git's own options or environment variables in that command name, such as `git -c diff.external=<program> diff`, `git -c core.hooksPath=<folder> commit` or `GIT_EDITOR=<program> git commit`, and a change of branch that such a program makes before the commit takes the staged ledger file, with its calls, to the other branch.
- [A `git add` that stages nothing comes before a commit that would otherwise commit nothing] → The commit holds the ledger file alone, where it would have failed without the tool, because the `PreToolUse` run cannot tell what the `git add` will stage.
- [A commit is refused, blocked, cancelled or interrupted after its ledger file was staged] → No run follows that command, so the file stays staged until a run of the step finds the command over and takes the file back: the session's next git command, turn end or end, or another session's next run in the repository. Until then, a git command finds the file staged, whether the person runs it outside the session or the agent runs it before the transcript shows the command's result: `git rebase` refuses to run, `git checkout` carries the file to another branch, where a commit takes it with its calls, and `git stash` takes it. A session whose process is killed during its commit, before the command's result is written, leaves the file staged until the person removes it or the session is resumed. A call that another hook defers leaves it staged until the call is resumed, unless a session-end run takes it back when the deferral ends the process, which Claude Code's documentation leaves open; either way the resumed commit carries the calls, in the file still staged or in a new one, unless that branch is no longer checked out by then, when the resumed run takes the file back first and the calls wait for their own branch, or, when that run finds the index lock held, leaves the file staged, and a commit that starts once the lock is free takes it, with its calls, to the other branch.
- [A git command starts while a run stages or takes back a ledger file] → It fails at the index lock, as when any two git commands meet in one worktree. A run holds the lock only for the one file it stages or takes back, and a take-back that finds the lock held leaves the file for a later run, rather than waiting or removing the lock. A take-back that runs while a commit is still running, after the commit has read the index, leaves the file deleted in the index and the working tree until the first later run that finds that commit checked out and the index free puts it back, so a commit that the person makes before then deletes it, and the agent's next commit stages its calls again, since no run found a commit holding the file. The run that puts it back undoes, once, a removal of the file that the index holds by then for another reason, as when the person restores the file and then removes it, or commits its deletion and then goes back to that commit with `git reset --soft`. A `git stash` made before that run, while that commit is checked out, takes the take-back's deletion with it, so that the run finds nothing to put back and the pop deletes the file from the working tree again. And once a run has found another commit checked out after a take-back, as after the person's commit that deleted the file, or after the agent's next commit when the take-back followed a reset in its commit's own command, a mixed `git reset` back to the commit that took the file brings it back into the index alone. Either way, a `git commit -a` then deletes the file, and its calls stay out once a run has found the commit holding it. A file that another command removes from the index while the commit runs stays removed, so the next commit deletes it, as it would without the step, and its calls stay out once a run has found the commit holding it.
- [A person removes a ledger file from their branch, or a commit that holds one is undone] → Once a run has found a commit holding the file, the script never stages its calls again in that run's clone, however the file is removed, so they stay out of the branch's later ledger files, and the comment does not count them unless the file itself is committed again. That holds for a commit that the agent or the person reverts, resets away in any mode but `--soft`, or splits in an interactive rebase, even when its changes are committed again. The script leaves such a file to git: a removal that leaves it in a working tree, untracked or with only an intent-to-add entry, as a mixed `git reset` or a `git rm --cached` and a commit do, leaves it there, as git leaves the other changes that a reset leaves. A `git commit -a` or a `git add -A` commits an intent-to-add entry, whatever ignore rule matches the file, and unless one does, `git add -A` stages an untracked one and `git stash -u` and a pop carry it to any worktree, so that a commit takes it again, with its calls, on whatever branch is checked out then, after a change of branch as well. That keeps the ledger files of a squash made with a mixed `git reset` and `git add -A`, and leaves a removal made for privacy to be undone by a later `git add` unless the person deletes the file as well, as a `git rm` without `--cached` does, which the README says. Until it is committed or deleted, the file also stops a checkout, a merge, a `git cherry-pick` or a `git reset --keep` that would bring back a commit holding it, as any untracked file in the way does unless an ignore rule matches it, and `git stash` fails while `git reset -N` has left an intent-to-add entry for it, as it fails for any such entry. Where an ignore rule matches `.pr-cost/`, `git add -A` leaves such a file out, and in a sparse checkout that leaves the folder out, as one in cone mode does unless it names that folder, `git add -A` refuses it, as it refuses any new file outside the sparse checkout, and exits with an error after staging the rest, so that a commit joined to it by `&&` does not run, while a command that applies the sparse patterns, such as a checkout, removes a committed ledger file from the working tree, so that a reset then leaves nothing there. In those cases a squash made with a mixed `git reset` can lose the ledger files of the commits it squashes, so the README tells adopters who use a sparse checkout to add `.pr-cost/` to it. A removal before any run has found the commit, as by a reset or a revert in the commit's own command, leaves the calls to the agent's next commit. A file that a later commit removes stays in git history, so such a removal hides nothing that was pushed, and a session resumed in a fresh clone at the same path, which has no store, can record again the calls of a file that its branch no longer holds.
- [A repository's own git hooks see the staged ledger file] → A `pre-commit` hook that refuses it fails a commit that would pass without the tool, and the agent sees that hook's message, which names the file; each retry stages the calls again. An agent that is shown such a failure, about a file it did not write, may retry with `--no-verify`, which also skips the hook's checks on its own changes, or change the hook's configuration to let the file through. The ledger names its hash field so that detect-secrets' default filters read the hash as an identifier, task 1.2 checks a ledger file against that scanner, and the README tells adopters to exclude `.pr-cost/` from their own git hooks before they turn the tool on. A scanner with other rules can still refuse the file.
- [A repository's settings act on the ledger path] → A sparse checkout that leaves out `.pr-cost/` would refuse to stage the file, so capture stages and takes back with `--sparse`. A `filter` attribute, such as Git LFS's for `*.jsonl`, can make git commit a pointer instead of the entries, and a `working-tree-encoding` makes git decode them as other text, from whichever attribute file sets them, so capture stages nothing where either applies, and the comment says that no agent usage was recorded. Where `core.safecrlf` is on and line endings are converted, git refuses to add the file, so capture stages nothing there either; a `.pr-cost/** -text` line in the root `.gitattributes` lets it through, unless git ranks above it a line that gives `text` another state for those files, such as `text`, `text=auto` or `!text`: a later line in that file, a line in a `.gitattributes` inside `.pr-cost/`, or one in `.git/info/attributes`. Where the line works, `git check-attr text` reports `unset` for a ledger path. The README says so.
- [A session works from a folder that contains the repository] → Its calls are not recorded, so its figure is too low. The README says to start a session in the repository.
- [A session whose current directory is in the repository also works on another one, through paths or with a `cd` inside a command] → Those calls are recorded here, because a line's working directory is Claude's current directory (decision 1). The README tells a person who opts in to keep other repositories' work, and above all private repositories', out of such sessions.
- [A session resumed in a fresh clone at the same path, on another branch, records calls that an earlier branch's ledger files already hold] → The report never counts a call the default branch already held, so such a call is counted once across pull requests, for whichever merges first.
- [A force-push removes commits that CI ran on] → Their runs are not counted, and the comment says that the CI minutes are those of the pull request's own commits.
- [A pull request is based on another one that was merged by squashing or rebasing] → The default branch does not hold the earlier pull request's commits by their hashes, so the later one counts their runs again, unless it is rebased first. The README says so.
- [A workflow runs a script or a local action that a pull request changes] → The comment flags changes to workflow files and to `.pr-cost.json`, not to the files that workflows run, which can also act with the identity that posts the report. Those changes are in the pull request's diff for review.
- [An adopter updates the hook and the workflow pin at different times] → Their price tables then differ. An older hook records a model that only the newer table lists as `unknown`, which the report counts in tokens and leaves out of the cost. An older report refuses a ledger line with a name its table does not list, and counts it as refused. Either way the comment shows that something was not priced, and nothing is guessed.
- [Capture fails without anyone seeing it, since a hook that succeeds shows nothing] → Refused calls are counted in the ledger, a failed run leaves its records for the next run, and a pull request whose capture never ran says that no agent usage was recorded.
- [A ledger edited by hand changes the reported cost] → The ledger is in the pull request's diff like any other file, and the report is an estimate, not a bill.
- [Cache writes recorded without their lifetime] → Decision 1 records the lifetime the transcript gives. Where it is absent, the report gives a range (see `cost-pricing`).
- [Prices go stale, or a new model appears] → Every report names the price table's date, and an unpriced model or attribute is named rather than guessed. A model the hook's copy of the price table does not list is recorded as `unknown` until the adopter updates the hook.
- [Capture and the report read the call ids of every ledger file that their branch holds, which grow with every pull request, and which whoever merged them wrote] → Both read them only as blobs from git, skip anything in the ledger folder that is not a regular file, and learn each file's size before reading it. The report refuses the ledger change when the files that a pull request adds are together above the size bound that the ledger format documents, capture skips any one file above that bound, and capture stops at its time budget. How long the reads take is measured in the end-to-end test, and what to do about it is decided from that measurement.
- [Mutation testing takes time in CI] → Its duration is measured when it is added, and what to do about it is decided then, from that measurement.

## Open Questions

- Whether to show a reasoning-token count separately. It is part of output tokens and priced the same, so this changes only the report's layout.
- Whether the calls of a ledger file that someone removes from their branch should stay out of its later ledger files, as decision 1 has it, which keeps a removal made for privacy, or come back in the agent's next commit, which keeps in the count the calls of a commit that is reverted or reset away, and those of a commit whose changes are committed again without its ledger file. A rule that brought back only the calls of work that is kept could not tell it from a removal by the file alone: in a sparse checkout that leaves out `.pr-cost/`, a reset that keeps a commit's changes can leave its ledger file as a removal does. Nor could it tell them apart by the commands that removed the file, which the step reads in its transcript for the agent and git records in its reflog for a reset: the same mixed `git reset` that takes the file out of a commit for someone who means to remove it also keeps a commit's changes to squash them with others.
