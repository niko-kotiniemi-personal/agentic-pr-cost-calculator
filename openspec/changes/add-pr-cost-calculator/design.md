# Design

## Context

See `proposal.md` for why. These facts shape the approach:

- Claude Code writes each session's transcript as JSON lines on the machine running the session. Each assistant message carries its model and a `usage` block with input, output, cache-write (split into five-minute and one-hour lifetimes) and cache-read tokens. Current versions also give the service tier, the speed, the inference region and the server-side tool requests, all of which can change the price. One message can be written over several transcript lines. In the main transcripts examined, every line of a message gave its stop reason and the same usage. Subagent transcripts were seen in two shapes. In some, a message's earlier lines gave partial usage and no stop reason, and only its last line gave the final usage and the stop reason. In others, almost no message had a line that gave a stop reason, and every line of such a message lacked fields that final lines carry, among them the server-side tool requests, and gave few output tokens even for a message that called tools: the usage of the call's start, not its end. Claude Code also makes model calls for some of its own tools: the description of its WebFetch tool says that it answers its prompt against the fetched page with a small fast model. Task 1.1 checks which of those calls the transcript records.
- Each transcript line names Claude's current directory at the time of the call. Claude Code keeps a `cd` from one command to the next only while it stays within the project directory and the directories added to the session, resets it after a command that leaves them, and never keeps one for a subagent. So a call that works elsewhere through absolute paths, with `git -C`, or with a `cd` inside its command, still names the directory Claude was in. The branch a line names was seen reading `HEAD` while a branch was checked out, so it is not used.
- Claude Code runs hooks at set points of a session. `Stop` runs when the main agent finishes responding, and not when the user interrupts it. `StopFailure` runs instead when a turn ends in an API error. `SubagentStop` runs when a subagent finishes, including the agents Claude Code runs for its own features, and names the subagent's own transcript as `agent_transcript_path`. `SessionEnd` runs when a session ends, as when the person exits or runs `/clear`, and its hooks share a budget of 1.5 seconds, which a hook's own `timeout` raises to match, up to 60 seconds. `PreToolUse` runs before a tool call, with a Bash command's text and the call's `tool_use_id` in its input, and before any permission prompt, and it runs again for a call that a hook deferred when that call is resumed. `PostToolUse` or `PostToolUseFailure` runs after a call that ran, as it succeeded or failed. A call refused at a permission prompt or by a rule, blocked by another hook, or cancelled while it runs gets neither; Claude Code documents that a blocked call's reason comes back to Claude as the call's error, and that a cancelled call's result carries the interruption message. A command run in the background, or moved there by Claude Code when it reaches its timeout, returns its result before it ends. Claude Code documents that the transcript is written asynchronously and can lag behind the conversation, and that all matching hooks run in parallel.
- A hook on a tool event can carry an `if` condition in permission-rule syntax, such as `Bash(git *)`, which Claude Code checks against each of the commands that a Bash input is made of, those inside `$()` included, and a hook with an `if` condition on any other event never runs. The condition matches a command as Claude wrote it, once leading variable assignments and a fixed list of wrappers, such as `timeout` and `nohup`, are stripped. So git run by its path, through `sh -c`, `env` or an environment runner, or through a shell alias or function does not match it, and Claude Code applies the aliases and functions of the person's shell start-up file to every Bash command. When Claude Code cannot tell which commands an input runs, it runs the hook anyway.
- Every hook receives the transcript's path and Claude's current directory, as `cwd`. A command hook runs in that directory, with two exceptions: in a worktree session started from the desktop app it runs in the main checkout's root, and when that directory no longer exists it runs from the first that still exists of the session's start directory, the project root, the home directory and the temp directory. `CLAUDE_PROJECT_DIR` names the project root, and stays there when Claude changes directory or enters a worktree. Claude Code creates its worktrees under `.claude/worktrees/` in the repository's folder. A hook's command runs in `sh`, in Git Bash on Windows, or, on Windows without Git Bash, in PowerShell, for which Claude Code rewrites `${CLAUDE_PROJECT_DIR}` into PowerShell's own form.
- What a hook's exit code and output do, as Claude Code documents them: Claude never sees the standard error of a hook that exits 0. A `PreToolUse` hook that exits 2 blocks the tool call. A `Stop` or `SubagentStop` hook that exits 2 sends Claude back to work with the hook's standard error as the reason, unless its standard output is empty and its standard error says that a file is missing, which Claude Code treats as a non-blocking error. JSON printed on standard output can block or approve whatever the exit code, except that an exit of 2 blocks whatever the JSON says. Python exits 2 when it cannot open its script, and says that the file is missing or that permission is denied. A command hook's default timeout is 600 seconds, and a timed-out `PreToolUse` hook does not block the tool call.
- A repository's `.claude/settings.json` can set environment variables for everyone who works in it, and they reach every process Claude Code starts, its hooks included. Claude Code ignores some variables from project settings, among them `HOME` and the `XDG_*` variables. Git reads its global configuration from the file that `GIT_CONFIG_GLOBAL` names when it is set, and `GIT_CONFIG_COUNT` with its companion variables adds settings.
- The checksum that the registered command carries (decision 1) relies on Claude Code keeping, for the rest of a session, the hook registrations that it read when the session started, so that a branch checked out during the session, which can change `.claude/settings.json` as well as the hook file, cannot change the command that a hook runs. Task 1.1 checks that Claude Code does so.
- On Windows, a program started by a name with no folder in it, such as `git`, is looked for first in the folder that the starting program was loaded from and in its current directory, and only then in the system's folders and in the folders that `PATH` names, as the documentation of `CreateProcess` says. Python's `os.path.expanduser` takes the home folder there from `USERPROFILE` and ignores `HOME`, as Python 3.11 was seen to do, while git takes it from `HOME`, and only when `HOME` is not set from `HOMEDRIVE` and `HOMEPATH`, or from `USERPROFILE`.
- In a partial clone, git fetches from the remote an object that a command needs and the clone lacks. With git 2.43.0, `git cat-file -s` on a ledger blob that a clone made with `--filter=blob:none` lacked fetched it, and with `GIT_NO_LAZY_FETCH=1` the same command exited with 128 and fetched nothing.
- A cloud session's machine is disposable, and the transcript is gone after it ends, so usage has to be captured during the session. Reading transcripts after the fact also turned out to be slow at the scale of a long pull request.
- GitHub's jobs API gives each job's start and end times with the default `GITHUB_TOKEN` and `actions: read`. It lists only the latest attempt of each job unless asked for all of them, and a job that has not finished has no end time. Its per-run "billable" timing figure was seen returning zero, so minutes are computed from job times.
- A squash merge puts one new commit on the default branch, and GitHub's rebase merge always makes new commits, so neither brings to the default branch the commits that CI ran on. A pull request's head stays readable from git as `refs/pull/<number>/head`.
- A reusable workflow receives its caller's `github` context, including the event that triggered the caller. The `job` context names the reusable workflow's own repository and commit. Events caused by `GITHUB_TOKEN`, such as a merge a workflow makes, start no new workflow run.
- GitHub's "List pull requests associated with a commit" lists, for a commit that the default branch holds, the merged pull request that introduced it, as GitHub's API description says, and for any other commit the merged and open pull requests associated with it. The report's rule for which push gets a comment rests on that description (decision 7). GitHub's rate limit for `GITHUB_TOKEN` is 1,000 requests per hour per repository, so the report's calls draw on a limit that the repository's other workflows share. GitHub's listing of a repository's workflow runs returns at most 1,000 runs when it is filtered, as by event, by creation time or by commit. `actions/checkout` fetches one commit unless it is asked for more.
- Anthropic's pricing has modifiers beyond the four token rates: higher rates for long prompts on some models, a multiplier for US-only inference, premium rates for fast mode, and a charge per web search. Web fetches cost nothing beyond their tokens.

## Goals / Non-Goals

**Goals:**

- Capture with no service outside GitHub and the repository itself.
- Keep everything a public repository can publish: counts, prices and totals, never content.
- Publish a person's usage only with that person's consent, which holds for each call and not only for the run that records it, and only the calls their sessions make from the repository that publishes it.
- Make every number in a report reproducible from the ledger, the price table and the jobs API.
- Treat everything that crosses into the tool as untrusted: transcripts, ledgers, API data, and the pull request being reported. `docs/threat-model.md` lists the threats and what answers each.

**Non-Goals:**

- Billing reconciliation. The figure is an API-equivalent estimate, and plans, discounts and included minutes are not modelled.
- Agents other than Claude Code in this change. The ledger format is documented so they can be added later.
- The cost of AI code review on the pull request, such as the tokens a review app or a review job in CI spends.
- Live cost while a pull request is open. The report runs at merge.
- GitHub Enterprise Server, which lacks the `job` context values that decision 7 relies on.
- Shell commands sent through Claude Code's PowerShell tool, which is on by default on Windows for claude.ai and Console accounts, always on there without Git Bash, and can be turned on elsewhere. A hook registered for Bash never runs for those commands, so capture stages nothing for a commit made through that tool and does not see a change of branch made through it. The hooks that run whatever the tool, when a turn, a subagent or a session ends, still run on Windows without Git Bash, in PowerShell, so the registered command is written to exit with success there too (DR-031).

## Decisions

### 1. Capture with Claude Code hooks, into the git directory, then into the agent's own commits

*Records:* DR-008, DR-009, DR-010, DR-011, DR-012, DR-013, DR-014, DR-022, DR-030, DR-031, DR-032, DR-033, DR-034, DR-035, DR-036, DR-052, DR-053, DR-054, DR-055, DR-056, DR-057, DR-058, DR-059, DR-060, DR-125, DR-127, DR-128, DR-129, DR-130, DR-135, DR-136, DR-137 and DR-138.

One script is registered for seven hook events: `Stop`, `SubagentStop`, `StopFailure` and `SessionEnd`, and `PreToolUse`, `PostToolUse` and `PostToolUseFailure` for Bash commands, with the condition `Bash(git *)`, so that around Bash commands it starts for those that run git as Claude writes it, and for any whose commands Claude Code cannot tell (see Context).

This repository is the one that holds `CLAUDE_PROJECT_DIR`, so a run means the same repository whatever directory Claude has moved to. Every run, whether a turn, a subagent, a failed turn or the session has ended or a git command is about to run or has run, reads the session's transcript on from where it last stopped, and the subagents' own transcripts, which Claude Code keeps in a `subagents/` folder nested under the session's. It keeps each call whose line gives a working directory in this repository: one whose git common directory is this repository's, so that the repository's worktrees count and a separate repository nested in its folder does not. Of those, it records only the calls made while both switches were on (decision 6). It records each such call in a store inside the repository's common git directory (`git rev-parse --git-common-dir`), outside the working tree and shared by every worktree, together with the worktree that git itself finds from the directory the call's line names, which for a directory inside a worktree under the repository's folder, as Claude Code's are, is that worktree and not the main checkout around it, and the branch checked out there when the call is recorded, or the fact that none was. Because a run comes before every Bash command that the condition matches, a call that the transcript holds as over by then is recorded before that command can change its branch, unless that run reaches its time budget before it reads the call. Apart from staging a ledger file, taking it back and putting it back, as below, it changes nothing in the working tree or the index, so recording never blocks switching branches or rebasing.

A call's usage is read from its lines that give a stop reason. Where none does, as in one shape of subagent transcript, the call is read from its last line once it is over: once a later call follows it in the same transcript, or once its agent has stopped, which `Stop`, `StopFailure` and `SubagentStop` say. The ledger counts the calls read that way, because their lines give the usage of the call's start, and the comment gives that count and says that the token cost is then a lower bound. A call that is not over yet waits for a later run. A call whose usage holds a field that the script does not know, at its top level or in a block nested in it, is recorded from the fields that the script knows, and the ledger counts such calls without naming the field, because a new field can carry a charge that the entry then leaves out, so the comment gives that count and says that the token cost may then be low. A run reads only the lines that end in a line break, because Claude Code can still be writing the last one, and a line that a run began with and could not finish reading within its time budget is skipped by the next run and counted as one refused call, so that no one line, however long, holds capture back for good.

Before a Bash command that runs `git commit` in this repository, the script first reads the transcripts as above. A command runs `git commit` when one of the commands it is made of, split as the shell splits it, is `git`, then any of git's own options, then `commit`, and is not a dry run, which it is when any of `--dry-run`, `--short`, `--porcelain`, `--long`, `-z` and `--null` is in effect once git has read the commit's options, in any spelling that git accepts, such as `--dry` or `-qz`. For git, `--short`, `--porcelain` and `--long` are one setting, which the `--no-` form of any of them clears, so `git commit --porcelain --no-short` makes a commit. A `PreToolUse` run comes before the whole command, so it cannot see what an earlier part of the command will stage, nor which branch a commit after an arbitrary command lands on, nor when a commit in the background will run. So the script stages a ledger file only when the commit is a top-level command, joined to the rest by `&&`, `;` or line breaks and not part of a pipeline, whose other commands run beside it, runs in the foreground, which a commit followed by `&` does not, and comes after nothing but `cd` to a path written in the command and the git commands `add`, `rm`, `mv`, `status`, `diff`, `log` and `show`, with or without git's own options, which are what an agent runs before a commit and which do not change the branch themselves. A command substitution or a process substitution runs before the commit, or beside it, wherever it is in the commit or in a command before it: in an argument, in a leading assignment, or in a redirection. So each counts as a command that comes before the commit, except one whose only command is `cat` reading a here-document whose delimiter is quoted, which is one way to pass a message of several lines, and in whose body the shell expands nothing. The shell runs any command substitution in the body of a here-document whose delimiter is not quoted, so when the commit or a command before it reads one, the script stages nothing. For any other command it stages nothing, and the calls wait for a later commit. The worktree where the commit runs is the hook input's `cwd`, followed through each top-level `cd` before the commit and the `-C` options given to git before `commit` in the commit's own command, never the directory the hook runs in, which in a desktop worktree session is the main checkout (see Context), and the script stages nothing when such a `-C` option names a path that is not written in the command. A `-C` given to an earlier git command does not move the commit, and a `-C` after `commit` names a commit whose message the commit reuses.

When it stages, the script writes the calls recorded for that worktree and the branch now checked out there, which no ledger file on that branch holds and which the store has not noted as taken, into one new file, `.pr-cost/ledger/<YYYY-MM>/<random>.jsonl`, created only if no file of that name exists, and stages that file alone, with `--force` so that an ignore rule cannot drop it, and `--sparse` so that a sparse checkout that leaves out `.pr-cost/` cannot refuse it. It writes nothing when no call is waiting; when the command names the paths to commit, which leaves the rest of the index out; when the commit would commit nothing without the file, counting the changes to tracked files that `-a` adds, and no `git add`, `git rm` or `git mv` comes before it, so a commit that would fail still fails, and an empty commit asked for stays empty; when a `git rm` or `git mv` before the commit is given a `-C` path not written in the command, or names a path with a wildcard or other pathspec magic, a path not written in the command, or the folder that the file goes in or one above it, read from where that command runs, after the `cd`s before it and its own `-C` options, because `git rm` refuses to remove a newly staged file and fails the command, and `git mv` moves it where the script does not look for it; and when `git check-attr`, which reads every attribute file that git does, the repository's `.git/info/attributes` and the person's own among them, gives the ledger path a `filter` or a `working-tree-encoding`, because git can then commit a pointer, as Git LFS does, or the file decoded from another encoding, instead of the entries. When git refuses to add the file, as it does where `core.safecrlf` is on and line endings are converted, the script removes the file it wrote and stages nothing. When a `git add` does come first and stages nothing, the commit holds the ledger file alone instead of failing, which is a residual.

After the command, its `PostToolUse` or `PostToolUseFailure` run checks whether the commit now checked out in that worktree holds the file. If not, that run takes the file back, from the index and the working tree, and its calls wait for a later commit. Once any run finds a commit holding a file that the script staged, the store notes the file's calls as taken, and the script never stages them again in that run's clone, so that in that clone a ledger file that someone removes from the branch later, in whatever way, takes its calls with it, even when the changes of its commit are committed again. From then on the script leaves the file to git, like any file that a commit took, and never takes it back: a removal that leaves it in the working tree, untracked or with only the intent-to-add entry that `git reset -N` leaves, as a mixed `git reset` or a `git rm --cached` and a commit do, leaves it where a later `git add -A`, or for an intent-to-add entry a `git commit -a`, commits it again, with its calls, on whatever branch is checked out then, as they commit the other changes that a reset leaves, unless a sparse checkout leaves it out, or an ignore rule matches it while it is untracked. So a squash made with a mixed `git reset` and `git add -A` keeps the ledger files of the commits it squashes, and their calls, except in the cases that the risks name. A command that was refused or blocked, and so never ran, or that was cancelled or interrupted, gets no such run, and an interrupt runs no `Stop` either. So the store notes, for each staged file, the session's id, the path of its transcript, which every run of that session brings up to date because Claude Code moves a session's transcript when the session enters or leaves a worktree, and the `tool_use_id` of the command the file was staged for. Any later run of the step in the repository, from that session or another, takes the file back once it finds that command over: by the command's result in the transcript, by a later call of the agent that ran it, by that agent having stopped, or by its session having ended, which `SessionEnd` says. A run takes back and puts back what it can before it reads any transcript, as a session-end run can for every file staged for its session's commands, so that a long transcript does not use up its time first. A `PreToolUse` run that fires again for the same `tool_use_id`, as for a deferred call when it is resumed, stages nothing new while that command's file is still staged and the branch it was staged for is still checked out in that worktree. When that branch is no longer checked out there, it takes the file back first, and then, as when a run has taken the file back meanwhile, it stages anew. A take-back never removes a file from a worktree whose checked-out commit holds it, and leaves the file while another git command holds that worktree's index lock, rather than waiting for the lock or removing it. A plain `git commit` holds no index lock once it has read the index, while its `prepare-commit-msg` and `commit-msg` hooks run, so a take-back can remove the file from the index after the commit has taken it, as when Claude Code moves a commit to the background at its timeout and returns its result early. A reset in the commit's own command, as in `git commit && git reset HEAD~1`, leaves the file where that command's run takes it back, too, while a later `git reset` can go back to that commit. So every take-back notes the commit that it found checked out there, not holding the file, and whether it removed the file from the index, the working tree or both, and the first later run that finds another commit checked out in that worktree and the index free puts the file back, as that commit holds it, if that commit holds it: into the index, if the take-back removed it from there and the index lacks it, and then into the working tree, if the take-back removed it from there, the index holds it as that commit does and the working tree lacks it, before the agent's next git command could commit its deletion. Then it forgets the note, whether it put the file back or not, so that a ledger file that the person removes later, or that the step never took back, is never put back. The script puts nothing back in any other case, so that a removal that the index holds stands, as after a `git reset --soft` back to a commit that holds the file, unless it comes while a put-back into the index is due, as the risks say. Another command can remove the file from the index in that window too, and the commit still holds it, while a take-back then finds the file only in the working tree: that removal stands as well, since the put-back into the working tree needs the index to hold the file, and the next commit deletes the file, as it would without the step. So does the removal from the index that a mixed `git reset` without `-N` in the commit's own command makes before the take-back, when a `git reset --soft` then goes back to that commit, and the next commit deletes the file, even one that `git add -A` makes, as the risks say. In a sparse checkout, too, the put-back puts the file into the working tree, where it would be had the step not taken it back. A put-back into the working tree puts nothing there that the index does not hold, so that a `git add` cannot stage a removed file again from it. A run that finds the index lock held leaves the note for a later run, as a take-back leaves its file. Apart from staging, taking back and putting back, no run touches the index.

A call is recorded once, by a SHA-256 hash of its message id. The store and the ids in the ledger files that the branch holds together say which calls are already recorded, so a session resumed in a fresh clone records nothing again that its branch already holds. A staged ledger file meets the repository's own git hooks, and a secret scanner can take a hash for a secret: by default, detect-secrets, a common one, flags a quoted hexadecimal string whose entropy is above a limit that SHA-256 digests exceed, unless text before it on its line names an identifier, such as a key that ends in `_id`. So the hash's field is named that way, and task 1.2 checks a ledger file against that scanner's default plugins and filters. An entry records the UTC day of the call and not its time, because pricing needs only the day, and a time on every call would show when a contributor works. An entry records whether the main agent or a subagent made the call, and no session value.

The registered command is `python3 -I -c "<check>" "${CLAUDE_PROJECT_DIR}/<script>" <checksum>; exit 0`, which finds the script whatever directory the hook runs in, with a timeout below Claude Code's default, and the script stops at a time budget inside that timeout, leaving what it has not read for its next run. Both values are set from measured run times when the hook is built. `<check>` is a few lines of Python, written with no character that `sh` or PowerShell reads inside double quotes, which read the script's file once and run what they read only when its SHA-256 is `<checksum>`, the checksum of the file that the adopter copied. The check relies on Claude Code keeping the registrations that it read when the session started (see Context). The script prints nothing on standard output, and lets no git command that it runs print there, since some do, as `git rm --cached` prints the path that it removes. Its standard error carries only its own words and numbers, never text from a transcript, from a ledger file or its name, or from what a git command printed. Calls it refuses are counted in the ledger, because no one sees the standard error of a hook that succeeds.

The script is one file that imports only Python's standard library, because under `python3 -I` a script cannot import a module beside it, and adding its folder to the import path would undo what isolated mode is for. Its first line names the release that it comes from. An adopter copies that file into their repository, at the path that the README gives, from the full commit that their calling workflow pins (decision 7), not from a tag, which can be moved, and checks it against the SHA-256 checksum that the README at that commit gives, which their registered command then carries. The checksum shows that the copy is whole, not that the commit is honest: that rests on the choice of commit, as it does for the workflow. From then on the file is reviewed and versioned with the rest of their repository, and an update is one pull request that replaces the file, the checksum in its registration and the workflow's pin together. An update bot can still move the pin alone and leave the file behind, so the report says when the hook file in the merged commit is not the one at the commit that the report runs from (decision 7). The file carries the model names and price attribute values of the price table at its commit, and records any other value as `unknown`, so that a gateway's private alias is not published. When the hook and the report come from one commit, they share one price table, and the report refuses a name that its table does not list.

The script starts no program but git, which it finds at an absolute path, in the folders that the absolute entries of `PATH` name, because Windows looks for a program named without a folder in the current directory before it looks in `PATH` (see Context), and Claude's current directory is usually in the repository. Before it starts git, it moves its own current directory to a folder that only the system's administrator can write, such as `/` or Windows' system folder, and names each git command's folder with `-C`, so that a program planted in Claude's current directory, in the repository's folder or in a folder that a relative entry of `PATH` names is never the one that runs. It reads both switches from their files before it starts any program, and a run that finds either off starts git only to note that in its store and to take back and put back what the store notes (decision 6). Every git command that it runs has `GIT_NO_LAZY_FETCH=1` and `GIT_TERMINAL_PROMPT=0` in its environment, so that in a partial clone a ledger blob that the clone lacks is skipped, as an oversized one is, rather than fetched (see Context), and no command asks for credentials: the hook opens no network connection.

The store is written only by replacing it whole, under a lock that the operating system releases when the process that holds it ends, so that a run killed while it writes leaves the store as it was or as that write left it, and leaves no lock behind. A ledger file is noted in the store before it is written, so that a later run takes back a file that a run killed while writing it left behind. Each session runs the script from the working tree that holds its project directory, and every worktree shares one store, so sessions started in two worktrees can run two releases of the script against one store. So the store carries the version of its format from the first release on, and a run that finds a version that it does not know records, stages, takes back and puts back nothing, leaves the store as it was, and exits with success.

### 2. Python, standard library only

*Records:* DR-023 and DR-126.

Development tools (pytest, ruff, mypy, detect-secrets for task 1.2's check, and the testing tools in decision 8) are pinned in `requirements-dev.txt`, and task 1.8 locks their own dependencies too, with hashes.

### 3. The ledger is the record, and the report writes nothing to the repository

*Records:* DR-010, DR-015, DR-016, DR-017, DR-127 and DR-131.

Because a ledger file is written once, under a random name, a pull request's usage is the ledger files its merge adds. Files the default branch already held, such as those that a reused branch name still carries from an earlier pull request, are not added again, so they are not counted again. An added entry whose call a ledger file held at any commit of the default branch's first-parent history before the merge is not counted, so that a ledger file that leaves the default branch, as a revert takes it, and comes back, as a revert of that revert brings it, is not counted twice, and an added file at a path that this history held is counted as restored. A change to an earlier ledger file is flagged, not counted. A ledger file that a pull request's merge removes is not lost: git history keeps it.

### 4. A dated price table as data in the repository

*Records:* DR-020, DR-124 and DR-155.

`prices/models.json` and `prices/github-actions.json` list each price with its effective date and the source page it came from, including the price modifiers that Context names, web fetches at no charge, and, for each model, statements of how its modifiers combine, each dated in the same way, since a change to how they combine changes a price as much as a change to a rate does. A change to a price or to such a statement is a pull request that adds a row dated after the rows already there, so history is never rewritten, and a change reprices nothing earlier.

### 5. Activity type from tool names

*Records:* DR-004 and DR-029.

The type comes from the first tool call in a message: edits and writes are code generation, reads and searches are file reading, shell commands are tooling, `mcp__` tools are MCP, starting a subagent is subagent, a tool the classification does not know is other, and no tool call is conversation.

### 6. The repository turns the tool on, and each person turns on their own capture

*Records:* DR-021, DR-046, DR-047, DR-048, DR-049, DR-050 and DR-051.

`.pr-cost.json` at the repository root holds `enabled`. Capture reads it in the working tree, and the report reads it as a blob from the default branch before and after the merge (decision 7), so the pull request being reported cannot turn its own report off. Both read it only as a regular file no larger than the size bound that its format documents, and take a file that is missing, larger, not a regular file or not valid to leave the tool off, so that the file cannot stall a run, as a named pipe in the working tree could, and a pull request that breaks it still gets its report, flagged, when the file before the merge turned the tool on.

Capture also needs the consent of the person whose session it records: `pr-cost.capture` set to `true` in their global git configuration.

The script reads that setting from the person's global configuration files, `~/.gitconfig` and git's file in the XDG configuration folder, not from files that they include, which can lie anywhere, a repository's folder among them, and ignores the variables that point git at other files or add settings, because a repository's settings can set those for everyone who works in it, though not `HOME` or the `XDG_*` variables. It takes the XDG folder from `XDG_CONFIG_HOME` only when that variable holds an absolute path, and reads `~/.config/git/config` otherwise, because git reads a relative one from its current directory, which can be in a repository's folder. It takes `~` from `HOME` only when that variable holds an absolute path, for the same reason, and never reads a configuration file from a relative path. On Windows, where `HOME` is not set or not absolute, it takes the folder that git takes when `HOME` is not set: `HOMEDRIVE` and `HOMEPATH` together where they name a folder that exists and is not Windows' system folder, and `USERPROFILE` otherwise. It does not use Python's `os.path.expanduser`, which there takes `USERPROFILE` and ignores `HOME` (see Context), and so would read another file than git does wherever `HOME` names another folder. Elsewhere, with no absolute `HOME`, it reads no file from `~`. Where both files set it, `~/.gitconfig` decides, as it does for git, which reads it after the other.

The script reads these files itself, since it reads both switches before it starts any program (decision 1), and it reads them by git's rules for its configuration files: section and key names match in any case, a value loses its quotes and any comment after it, the last value in a file decides, and a key in a subsection, such as `[pr-cost "x"]`, or in a comment is not the setting.

A run that finds either switch off records nothing, but the session's calls stay in its transcript, where a later run that finds both on would read them, since every run reads on from where the last one stopped. So the store notes, for each session, each run that finds both switches on and each that finds either off, and the script creates the store for that where there is none. It records only the calls whose transcript time falls inside an interval when both were on: from the session's start, when the session's first run finds both on, or else from a run that finds both on after one that found either off, up to the last run that finds both on before the next one that finds either off. A run that finds the person's own capture off, in their global configuration or in the repository's, ends that interval for every session that the store notes, and no call made before that run is staged after it, so that turning capture off also withholds what was recorded and not yet committed. Taking back and putting back ledger files does not wait on the switches, so a file staged before capture was turned off is still taken back. The script cannot tell when a setting changed between two runs, so a person who opts in during a session, before its first run, has that session's calls recorded from its start, as the risks say.

### 7. The report runs on the push that a merge makes to the default branch

*Records:* DR-017, DR-018, DR-019, DR-039, DR-051, DR-061, DR-062, DR-063, DR-064, DR-065, DR-124, DR-131, DR-132, DR-133, DR-139 and DR-156.

The tool provides a reusable workflow. A repository calls it from a workflow of its own, triggered by `push` to its default branch, which grants `contents: read`, `actions: read` and `pull-requests: write` and passes no secrets. The README gives that caller, pinned to a full commit of this tool.

A reusable workflow receives its caller's event, so the report checks the event itself and refuses anything but a push to the default branch: it goes on only when `github.event_name` is `push` and `github.ref` is `refs/heads/` followed by the default branch's name, so that no other event passes, even one whose `github.ref` names the default branch, and neither does a push of a tag named like the default branch, whose `github.ref_name` is that same name. It checks out its own code by `job.workflow_repository` at `job.workflow_sha`, which name the reusable workflow's commit and not the caller's, and runs it with `python3 -I`, reading the caller's repository only as data. It fetches what it reads, since `actions/checkout` fetches one commit unless it is asked for more: the default branch's history up to the push's commit, and the pull request's head as `refs/pull/<number>/head`.

The report finds the merged pull request with GitHub's "List pull requests associated with a commit", which for a commit on the default branch returns the merged pull request that introduced it (see Context). It looks up each commit that the push adds to the default branch's first-parent history, and when they do not all belong to one pull request, as when a merge queue merges several in one push, or belong to none, as when a commit is pushed straight to the default branch, it posts no comment and says why in its job summary, so that a push that gets no report can be told from a report that did not run. It reads the ledger from git, comparing the push's commit before with the one after: the ledger files the merge adds, and the earlier ledger files it removes or changes, whose number the job summary gives when the push gets no comment. So that a call is counted once, it also reads the call ids of every ledger file that a commit of the default branch's first-parent history held before the merge, and counts as restored an added file at a path that this history held. It reads those earlier files by the rules that capture applies to the ledger files it reads: it skips a path that is not a regular file, a file above the size bound and a line that does not match the ledger format, and counts none of them against the pull request, since none of them is the pull request's, so that a ledger file that an earlier merge brought can neither stop nor slow every later report. It reads `.pr-cost.json` at both commits only as a blob within the size bound that its format documents, takes a file that is missing, not a regular file, too large or not valid to leave the tool off at that commit, and runs when either commit turns the tool on, so the pull request that turns the tool on gets its report too, and so does one that breaks the file.

The report's calls to GitHub's API grow with what the pull request's author controls, such as how many commits it has and how many runs they start, while the requests that `GITHUB_TOKEN` can make each hour are limited for the whole repository (see Context). So the report keeps to a call budget that the README gives, and its job has a time limit, set with `timeout-minutes`. It finds the runs on the pull request's commits with as few calls as it can: by listing each commit's runs, or, where fewer calls do it and GitHub returns the whole listing, by listing the repository's runs page by page, filtered by their event and by when they were created. When the budget runs out before the report can tell which pull request the push merges, it posts no comment and says so in its job summary. When it runs out while the report reads the runs and jobs, or GitHub returns only part of a listing, the comment marks the CI cost as incomplete.

The CI cost comes from the pull request's own commits, which the report reads from git as those that `refs/pull/<number>/head` holds and the default branch did not hold before the merge, because a squash or rebase merge brings new commits that no CI ran on. It counts only the runs on those commits that no push to the default branch started, as the event and branch that each run names show, and that were created before the pull request merged. So the runs that the merge's push starts, the report's own included, are not counted, even when they run on one of those commits, as after a fast-forward, and this does not depend on how their creation times fall around the merge time. A run that the merge starts through another event, such as a workflow on the pull request's `closed` event, is left out because it is created at the merge or after it. GitHub does not document that order, so the threat model states it as an assumption, which this repository cannot check, since none of its own workflows runs on such an event. A run counted that has not finished makes the CI cost incomplete, and a job on a runner that the price table does not list is counted in minutes and left out of the cost. Commits that a force-push removed from the pull request's head are no longer in that ref, so runs on them are not counted, and the comment says that the CI minutes are those of the pull request's own commits.

The report flags a change to `.pr-cost.json`, to the hook file at the path that the README gives, or to any workflow file, because any workflow in the repository can run with the identity that posts the comment, and so could change it later, and the hook runs on the machine of everyone who works in the repository. It also says when the hook file in the merged commit is missing or differs from the hook file at `job.workflow_sha`, quoting nothing from it, because adopters' update bots can move the workflow's pin and leave the copied hook behind, so that the hook and the report come from different commits.

### 11. Releases by semantic version, from a tag, with a bill of materials

The release workflow is written in Python, apart from the YAML that GitHub requires to start it. It checks the tag's form before any other step, then the tag against `pyproject.toml`, the changelog and the surface manifest, writes a software bill of materials in CycloneDX JSON with a standard-library script, runs the private-reference check over the bill of materials and the release's text, and publishes a GitHub release whose fixed text names the tag and the commit, followed by the changelog entry, with the bill of materials attached.

The release job is the only one that holds `contents: write`, and it runs only for a tag. The tool has no dependencies beyond Python's standard library, so its bill of materials is short, and it is built from the tagged tree, as `git ls-tree -r` lists it, never from a working tree, which can hold untracked files. It names the tool, its version, the commit, its licence, the oldest supported Python as `requires-python` gives it, the hook file's SHA-256, each action the reusable workflow uses, at its pinned commit, since the report runs them, and the vendored and generated parts, Superpowers and the OpenSpec skills, as development-only components with their source and licence, since GitHub's source archive of the release holds them. ### 13. Each decision has a record of its own

*Records:* DR-108, DR-119, DR-120, DR-121, DR-151, DR-152, DR-153, DR-158 and DR-159.

The records are in `docs/decisions/`, one Markdown file each, named `DR-NNN-<words>.md` with the number in ASCII digits, padded to three, and `docs/decisions/README.md` is their index, with one row per record giving its title, type, status, decider, requirements and threats. The folder holds nothing else, each record a file and not a link, and no file elsewhere is named as a record. A record opens with its heading, `# DR-NNN: <title>`, and seven fields, in this order: its type (scope, architecture, technical, security and privacy, or process), its status (accepted or closed), who decided it, the requirements and the threats it shapes, the records it replaces and the record that closed it. Its sections follow, each once and in this order: Context, Decision, Alternatives, Consequences, Scope, and What reversing it would change. "Decided by" takes one of three forms: the owner, with the dates of the decision, as in "the owner, 2026-10-20"; the change that decided it, as in "the change `add-pr-cost-calculator`"; or that change with the dates on which the owner asked for what it then decided, as in "the change `add-pr-cost-calculator`, as the owner asked on 2026-10-18". Numbers run from DR-001 in the order that records are added, whatever their type.

A record holds one choice: what was decided, why, what else was considered, what follows from it, what it covers, and what reversing it would change. This design keeps how the tool carries each choice out and names, under each decision, the records that hold its reasons; the specs keep the requirements, which a record names by ID. A record names requirements, threats and other records by ID, its change by name, and that change's design decisions and tasks by number, and the tests resolve each of them, finding a design decision or a task named without its change in any change, active or archived; the design, the proposal and the tasks that it names without naming a change are those of the change that added it. It may name a file by its path, which no test resolves, so a record describes the tree as it stood when it was accepted. It holds only printable ASCII characters and line breaks, and links only from a record's ID to that record's file. A record whose choice bears on every threat alike, as how threats are rated does, lists no threat and says why. It describes and never instructs; what steers an agent stays in `CLAUDE.md`.

A record that the default branch holds is accepted: the owner's merge of the pull request that adds it is the acceptance. When a later decision changes any part of a record, the record is closed as a whole by a new record that replaces it and restates whatever still holds, so that no record is ever partly in force. The closed record's status becomes closed and its "Closed by" names the new record, which names it in "Replaces". Nothing else in an accepted record changes, and no record is removed. Once a record is closed, any line of text under its sections may become `[removed]`, as for private text that reached it, and nothing else in it changes. A mistaken merge's records are undone in the same way, by records that close them.

`tests/test_decisions.py` holds what a machine can check of this: the form, the numbering, the folder, the index, the citations, the mentions of records and design decisions in tracked files and of requirements, threats, changes and tasks in Markdown files, the attributes that would hide a record's diff, the rule that each threat an accepted record lists names that record in its Held by line, so that the change that closes a record meets the threats that rest on it, and the rule that a record the default branch holds changes only to be closed. That rule compares git trees, never the working tree: every file with a record's name anywhere in the base commit's tree, by path, mode and object, against HEAD's, with no rename detection, so that a record renamed, moved or replaced by anything else counts as removed or changed. The base is the merge base of HEAD and `refs/remotes/origin/main`, resolved by its full name so that neither a tag nor a local branch can take its place, and in CI also the commit that the workflow names in `BASE_COMMIT`, the pull request's base commit or the commit that a push to the default branch replaced, since a pull request's base is the branch that its author chose. The job that runs the tests clones the whole history for them, runs on every push to the default branch, and runs again when a pull request's base changes, as on any edit of its title or description, which GitHub reports as the same event. The check fails when a base cannot be found, saying how to fetch it, and skips only while no base's tree holds `docs/decisions/`, failing when a base holds that folder with no file in it named as a record. The release's test job names the commit of the previous release's tag as its base (task 6.3), and the checks of tasks 1.9 and 3.1 compare with the same base. Threat IDs, like requirement IDs, are retired rather than reused, and the threat model lists the retired ones.

## Risks / Trade-offs

- [Claude Code changes its transcript format] → The parser keeps to the fields it needs, refuses unknown shapes with a count instead of guessing, and its fixtures carry every shape seen in each kind of transcript, so a change shows up as a failing test. Two final lines of one call that disagree, or a usage block whose cache-write split disagrees with its total, are refused. A usage field that the parser does not know is not a reason to refuse the call, whose known fields still price it, but the ledger counts such calls, and when there are any, the comment gives their number and says that the token cost may be low, because the new field can carry a charge that the entry leaves out.
- [Claude Code makes model calls for its own tools, such as WebFetch, that the session's transcript does not record] → Those calls are not counted. Task 1.1 checks which of Claude Code's own model calls the transcript records, and the comment and the README say that the calls it does not record are not counted.
- [A call read without a stop reason gives the usage of its start, not of its end] → Its output tokens and server-side tool requests are too low. The ledger counts such calls, and when there are any, the comment gives their number and says that the token cost is a lower bound.
- [Some calls reach no commit] → A call waits for a `git commit` that capture stages for, made in the worktree and on the branch where the call was recorded. So these calls are not in any pull request's ledger:
  - calls made after the agent's last such commit on a branch, such as pushing and opening the pull request, and the call that runs that commit, if that commit's run cannot yet read it as over, as it never can in a subagent transcript whose lines give no stop reason, and as it cannot when the transcript lags behind, and any call that that commit's run leaves unread at its time budget;
  - calls recorded on a branch that gets no later commit, such as the default branch before the agent branches off, or in a worktree where nobody commits, or one that Claude Code removes when a subagent finishes without changes;
  - calls recorded while no branch is checked out, as during a rebase that stops at a conflict, unless a commit is made the same way.

  Calls also wait, and may reach no commit, when the agent commits in a way that capture does not stage for: `git merge`, `git cherry-pick` or `git rebase --continue`, a script, a commit made through an API or through Claude Code's PowerShell tool, a commit in the background, in a pipeline, in a subshell or a group, joined to another command by `||`, or behind a wrapper such as `timeout`, one that follows another command in the same input, one whose message another command writes or a here-document whose delimiter is not quoted holds, or one made by git written in a form that the hook's condition does not match, as Context lists them. They wait too while a repository's own git hook refuses the ledger file, and in a repository whose attributes give the ledger path a filter or a working-tree encoding, or where git refuses to add the file, no call reaches a commit. The comment counts the usage that the pull request's commits carry, and the README says so and names these cases.
- [A call is recorded on the branch checked out when it is recorded, which can differ from the one it was made on] → A run before every Bash command that the hook's condition matches narrows this to three cases. One is the call that runs a command that changes the branch, when that command's run cannot yet read it as over. Another is any call that that command's run leaves unread at its time budget. The third is calls followed by a change of branch that no command the condition matches makes: one that a script or the person makes, one made through Claude Code's PowerShell tool, or one made by git written in a form that the condition does not match, such as by its path, through `sh -c`, `env` or an environment runner, or through a shell alias or function. Those calls go to the branch checked out next. A command that the script stages for can also run a program that git's own options or environment variables in that command name, such as `git -c diff.external=<program> diff`, `git -c core.hooksPath=<folder> commit` or `GIT_EDITOR=<program> git commit`, and a change of branch that such a program makes before the commit takes the staged ledger file, with its calls, to the other branch.
- [A `git add` that stages nothing comes before a commit that would otherwise commit nothing] → The commit holds the ledger file alone, where it would have failed without the tool, because the `PreToolUse` run cannot tell what the `git add` will stage.
- [A commit is refused, blocked, cancelled or interrupted after its ledger file was staged] → No run follows that command, so the file stays staged until a run of the step finds the command over and takes the file back: the session's next git command, turn end or end, or another session's next run in the repository. Until then, a git command finds the file staged, whether the person runs it outside the session or the agent runs it before the transcript shows the command's result: `git rebase` refuses to run, `git checkout` carries the file to another branch, where a commit takes it with its calls, and `git stash` takes it. A session whose process is killed during its commit, before the command's result is written, leaves the file staged until the person removes it or the session is resumed. A call that another hook defers leaves it staged until the call is resumed, unless a session-end run takes it back when the deferral ends the process, which Claude Code's documentation leaves open; either way the resumed commit carries the calls, in the file still staged or in a new one, unless that branch is no longer checked out by then, when the resumed run takes the file back first and the calls wait for their own branch, or, when that run finds the index lock held, leaves the file staged, and a commit that starts once the lock is free takes it, with its calls, to the other branch.
- [A git command starts while a run stages or takes back a ledger file] → It fails at the index lock, as when any two git commands meet in one worktree. A run holds the lock only for the one file it stages or takes back, and a take-back that finds the lock held leaves the file for a later run, rather than waiting or removing the lock. A take-back that runs while a commit is still running, after the commit has read the index, leaves the file deleted in the index and the working tree until the first later run that finds that commit checked out and the index free puts it back, so a commit that the person makes before then deletes it, and the agent's next commit stages its calls again, since no run found a commit holding the file. The run that puts a file back, after such a take-back or one that followed a reset in the commit's own command, undoes, once, a removal of the file made before that run: one from the working tree alone, as when the person restores the file and then deletes it with `rm`, and, after a take-back that removed the file from the index, one that the index holds by then for another reason, as when the person restores the file and then removes it with `git rm`, or commits its deletion and then goes back to that commit with `git reset --soft`. A `git stash` made before that run, while the commit that took the file is checked out, takes the take-back's deletion with it, so that the run finds nothing to put back and the pop deletes the file from the working tree again. And once a run has found another commit checked out after a take-back, as after the person's commit that deleted the file, or after the agent's next commit when the take-back followed a reset in its commit's own command, a mixed `git reset` back to the commit that took the file brings it back into the index alone. Either way, a `git commit -a` then deletes the file, and once a run has found the commit holding it, its calls stay out in that run's clone. After a mixed `git reset` without `-N` in the commit's own command, which takes the file out of the index before the take-back, a `git reset --soft` back to that commit leaves the index without it, so the run that finds that commit checked out puts nothing back and notes the file's calls as taken, and the next commit deletes the file, even one that `git add -A` makes. A file that another command removes from the index while the commit runs stays removed, so the next commit deletes it, as it would without the step, and once a run has found the commit holding it, its calls stay out in that run's clone.
- [A person removes a ledger file from their branch, or a commit that holds one is undone] → Once a run has found a commit holding the file, the script never stages its calls again in that run's clone, however the file is removed, so they stay out of the branch's later ledger files, and the comment does not count them unless the file itself is committed again. That holds for a commit that the agent or the person reverts, resets away in any mode but `--soft`, or splits in an interactive rebase, even when its changes are committed again. The script leaves such a file to git: a removal that leaves it in a working tree, untracked or with only an intent-to-add entry, as a mixed `git reset` or a `git rm --cached` and a commit do, leaves it there, as git leaves the other changes that a reset leaves. A `git commit -a` or a `git add -A` commits an intent-to-add entry, whatever ignore rule matches the file, unless a sparse checkout leaves its folder out. Unless an ignore rule matches an untracked one, or a sparse checkout leaves its folder out, `git add -A` stages it, and unless an ignore rule matches it, `git stash -u` and a pop carry it to any worktree. So a commit can take such a file again, with its calls, on whatever branch is checked out then, after a change of branch as well. That keeps the ledger files of a squash made with a mixed `git reset` and `git add -A`, and leaves a removal made for privacy to be undone by a later `git add` unless the person deletes the file as well, as a `git rm` without `--cached` does, which the README says. The README gives each `git rm` of a ledger file `--sparse`. Git needs it where a sparse checkout leaves `.pr-cost/` out, and where the file's entry carries the skip-worktree bit, which a sparse checkout sets on what it leaves out of the working tree and which a crash can also leave on an entry in a folder that the sparse checkout holds, while for an entry without that bit, in a repository without a sparse checkout, a `git rm`, `git rm -f` or `git rm --cached` does the same with `--sparse` as without it. Until such a file is committed or deleted, an untracked one also stops, as any untracked file in the way does, unless an ignore rule matches it, which lets git overwrite it, or a sparse checkout leaves its folder out, a `git checkout` or `git switch` without `-f` to a commit that holds it, and any of these that would bring it back: a merge, a `git cherry-pick` or `git revert`, with or without `-n`, a `git rebase`, a `git reset --keep` and a `git reset --merge`. While the file is in the working tree, the intent-to-add entry that `git reset -N` leaves stops the same commands, except a `git switch --discard-changes`, whatever ignore rule matches it, in a sparse checkout too, and, as any such entry does, also stops any `git rebase`, any `git cherry-pick` or `git revert` not given `-n`, any merge that is not a fast-forward, any `git reset --merge`, and forms of `git stash` that save or apply changes, such as a plain `git stash`, a `git stash create`, and a plain `git stash apply` or `git stash pop`. Some of these change things before they fail, such as a `git stash branch` of a stash that holds no staged changes, which can check out its new branch, and a plain `git stash apply` or `git stash pop` of a stash that holds untracked files, which restores those files, so that once the intent-to-add entry is gone, the same command run again applies the stash's other changes and then fails on those files, keeping the stash. Some forms of `git stash` that save or apply changes run all the same, and some of those drop the entry, as a `git reset --keep` to a commit that lacks the file does: among them a `git stash push --staged` or `git stash save --staged` given no other option or pathspec, when other changes are staged, and a `git stash apply --index`, `git stash pop --index` or `git stash branch` of a stash that holds staged changes, the last when that stash was made on a commit that lacks the file. A command that drops the entry leaves the file untracked where the working tree holds it, so that a squash made with `git reset -N` then loses it at a `git commit -a`, or at a `git add -A` where an ignore rule matches it. An `rm` of the file leaves its intent-to-add entry, which still stops commands such as a `git rebase`, a `git cherry-pick` or `git revert` not given `-n`, and a plain `git stash apply` or `git stash pop`, until a `git rm --sparse` removes the entry too, while a `git rm -f --sparse` removes both at once. A `git checkout` or `git restore` that copies from the index to the working tree the path of an intent-to-add entry, such as a `git checkout -- .` or a `git restore .pr-cost`, writes the entry's empty content over the file, so that a ledger file loses its calls. A checkout of the file's path from a commit that holds it, such as `git checkout <commit> -- .pr-cost`, runs whether the file is untracked or has an intent-to-add entry, and puts that commit's file in the working tree and stages it. Where an ignore rule matches an untracked one and no sparse checkout leaves its folder out, it still stops a `git checkout` or `git switch` without `-f` to a commit that holds it, and a merge that fast-forwards to one, even with `--squash`, when they are given `--no-overwrite-ignore`, while any other merge that brings it back overwrites it even then. Where an ignore rule matches `.pr-cost/`, `git add -A` leaves an untracked one out, and in a sparse checkout that leaves the folder out, as one in cone mode does unless it names that folder, `git add -A` refuses an untracked one, as it refuses any new file outside the sparse checkout, and exits with an error after staging the rest, so that a commit joined to it by `&&` does not run, while it and `git commit -a` leave out an intent-to-add entry there without an error, and a command that applies the sparse patterns, such as a checkout, removes a committed ledger file from the working tree, so that a reset then leaves nothing there. In those cases a squash made with a mixed `git reset` can lose the ledger files of the commits it squashes, so the README tells adopters who use a sparse checkout to add `.pr-cost/` to it, and to run `git sparse-checkout` only while no file has an intent-to-add entry, such as the ones that a squash made with `git reset -N` leaves for the files that the commits it squashes add, ledger files among them. The command `git ls-files -s --full-name -- ':/'` shows each such entry, wherever it is run, with the object name of an empty file, which begins `e69de29` under SHA-1, git's default hash, as it shows any other file whose content in the index is empty, though no ledger file that the step writes is empty, while `git status --short` shows such an entry as deleted when its file is, and not at all when the entry carries the skip-worktree bit. So that a committed empty file does not read as an entry, the README's way to tell leaves out a path that `git ls-tree -r --full-tree HEAD` shows with the same object name, unless `git diff --cached --name-status --no-renames --no-relative` shows the path as deleted, as it does for an entry that `git add -N` made for a committed empty file after a `git rm --cached`, while a file staged empty since the commit checked out still shows as one. Each of these three commands prints every path from the top of the worktree wherever it is run, while without `--full-name`, `git ls-files` prints paths from the folder it is run in, without `--full-tree`, `git ls-tree` lists only that folder, and without `--no-renames`, `git diff` can show an entry's path as renamed to an empty file staged since the commit checked out, and without `--no-relative`, prints paths from the folder it is run in where `diff.relative` is set. With any intent-to-add entry, git 2.43 can crash in a cone-mode `git sparse-checkout` command, such as an `add`, `set`, `reapply` or `init`, including a `set` or `init` that starts a sparse checkout, and with the sparse index on, or given `--sparse-index`, such a command can instead exit with success having written a damaged index, which repeats one path in place of others, so that the next commit deletes those others from the branch, which can include ledger files, and `git fsck` reports duplicate entries in that commit's tree. In the `git reset -N` of a squash whose commits add a file that the sparse checkout leaves out, git 2.43 can also, with the sparse index on and no intent-to-add entry before it, crash, leaving `index.lock`, or exit with success having written such a damaged index, after which the next `git commit -a` deletes ledger files from the branch. With the sparse index off, as it is unless someone turns it on, that squash keeps the ledger files where the sparse checkout holds `.pr-cost/`, and each damaged index described here comes with the sparse index on or given, so the README also tells adopters to keep it off in every worktree while the tool is on, and to give no command `--sparse-index`. A `git config --worktree index.sparse false` turns it off only in the worktree where it runs, while a setting in the repository's or the global configuration, or in a worktree's own configuration, which `--sparse-index` writes and `git worktree add` copies into the worktree it adds, keeps it on wherever that command has not run, as in a worktree that `claude --worktree` makes for a session. So the README's way to turn it off sets `git config index.sparse false` for the repository, which a worktree added later reads too, and runs `git config --worktree index.sparse false` in each worktree that `git worktree list` names, a command that git refuses with more than one worktree where `extensions.worktreeConfig` is off, as in a sparse checkout set up by hand, where the first command alone turns it off in every worktree. A crash can leave things behind that the README says how to clear, such as these. A crash of an `add` or `set`, or of an `init` that starts a sparse checkout, leaves the lock `info/sparse-checkout.lock` in the folder that `git rev-parse --git-dir` prints, and the lock stops a later `add` or `set` until it is removed. A crash of a `set` or `init` that starts a sparse checkout also leaves it on with no patterns, so that an `add` fails until a `set` or `init` writes them. A crash of a command given `--sparse-index`, or run while the sparse index is on, can also leave `index.lock` in that folder, with the sparse index on in the worktree's configuration, which can make `git status`, `git commit` and the step's staging fail. Such a crash can also have removed committed files, ledger files among them, from the working tree without setting their skip-worktree bit, so that a `git commit -a` deletes them from the branch. The README's way back from a crash or a damaged index turns the sparse index off, as its way to turn it off does, before it removes `index.lock`, since a `git status` run while the sparse index is on and that lock is gone can crash again or write a damaged index, and only then refreshes the index, as a `git status` does, so that its later steps start from an index whose file data match the working tree. The way back uses neither a mixed `git reset`, which can leave a file out of the index it rebuilds from a damaged one, so that the next commit deletes that file from the branch, nor a `git checkout` or `git restore` that copies from the index to the working tree a path that has an intent-to-add entry, such as a `git checkout -- .`, which brings back the files that a crash removed but also empties each file that has such an entry and undoes the person's own changes. A removal before any run has found the commit, as by a reset or a revert in the commit's own command, leaves the calls to the agent's next commit. A file that a later commit removes stays in git history, so such a removal hides nothing that was pushed, and a session resumed in a fresh clone at the same path, which has no store, can record again the calls of a file that its branch no longer holds.
- [A repository's own git hooks see the staged ledger file] → A `pre-commit` hook that refuses it fails a commit that would pass without the tool, and the agent sees that hook's message, which names the file; each retry stages the calls again. The worst case is a secret scanner that refuses the ledger file: an agent that is shown such a failure, about a file it did not write, may retry with `--no-verify`, which skips the scanner for the agent's own changes too, so that a secret in them is committed unchecked, or may change the scanner's configuration to let the file through. The ledger names its hash field so that detect-secrets' default filters read the hash as an identifier, task 1.2 checks a ledger file against that scanner, and the README tells adopters to exclude `.pr-cost/` from their own git hooks before they turn the tool on. A scanner with other rules can still refuse the file.
- [A repository's settings act on the ledger path] → A sparse checkout that leaves out `.pr-cost/` would refuse to stage the file, so capture stages and takes back with `--sparse`. A `filter` attribute, such as Git LFS's for `*.jsonl`, can make git commit a pointer instead of the entries, and a `working-tree-encoding` makes git decode them as other text, from whichever attribute file sets them, so capture stages nothing where either applies, and the comment says that no agent usage was recorded. Where `core.safecrlf` is on and line endings are converted, git refuses to add the file, so capture stages nothing there either; a `.pr-cost/** -text` line in the root `.gitattributes` lets it through, unless git ranks above it a line that gives `text` another state for those files, such as `text`, `text=auto` or `!text`: a later line in that file, a line in a `.gitattributes` inside `.pr-cost/`, or one in `.git/info/attributes`. Where the line works, `git check-attr text` reports `unset` for a ledger path. The README says so.
- [A session works from a folder that contains the repository] → Its calls are not recorded, so its figure is too low. The README says to start a session in the repository.
- [A session whose current directory is in the repository also works on another one, through paths or with a `cd` inside a command] → Those calls are recorded here, because a line's working directory is Claude's current directory (DR-057). The README tells a person who opts in to keep other repositories' work, and above all private repositories', out of such sessions.
- [A session resumed in a fresh clone at the same path, on another branch, records calls that an earlier branch's ledger files already hold] → The report never counts a call the default branch already held, so such a call is counted once across pull requests, for whichever merges first.
- [A force-push removes commits that CI ran on] → Their runs are not counted, and the comment says that the CI minutes are those of the pull request's own commits.
- [A pull request is based on another one that was merged by squashing or rebasing] → The default branch does not hold the earlier pull request's commits by their hashes, so the later one counts their runs again, unless it is rebased first. The README says so.
- [A workflow runs a script or a local action that a pull request changes] → The comment flags changes to workflow files, to `.pr-cost.json` and to the hook file, not to the files that workflows run, which can also act with the identity that posts the report. Those changes are in the pull request's diff for review.
- [An adopter updates the hook and the workflow pin at different times] → Their price tables then differ. An older hook records a model that only the newer table lists as `unknown`, which the report counts in tokens and leaves out of the cost. An older report refuses a ledger line with a name its table does not list, and counts it as refused. Either way the comment shows that something was not priced, and nothing is guessed. Whenever the hook file in the merged commit is not the one at the report's commit, the comment also says that the repository's hook does not come from the report's commit, quoting nothing from the file, and the README tells adopters to update both in one pull request.
- [Capture fails without anyone seeing it, since a hook that succeeds shows nothing] → Refused calls are counted in the ledger, a failed run leaves its records for the next run, and a pull request whose capture never ran says that no agent usage was recorded.
- [A ledger edited by hand changes the reported cost] → The ledger is in the pull request's diff like any other file, and the report is an estimate, not a bill.
- [Cache writes recorded without their lifetime] → Decision 1 records the lifetime the transcript gives. Where it is absent, the report gives a range (see `pricing`).
- [Prices go stale, or a new model appears] → Every report names the price table's date, and an unpriced model or attribute is named rather than guessed. A model the hook's copy of the price table does not list is recorded as `unknown` until the adopter updates the hook.
- [Capture and the report read the call ids of every ledger file that their branch holds, and the report those of every ledger file that the default branch's first-parent history held before the merge, which grow with every pull request, and which whoever merged them wrote, while capture's store grows with every call it records] → Both read ledger files only as blobs from git, skip anything in the ledger folder that is not a regular file, and learn each file's size before reading it. The report refuses the ledger change when the files that a pull request adds are together above the size bound that the ledger format documents, capture and the report skip any one earlier file above that bound, capture stops at its time budget, and the report's job at its time limit. How long the reads take, the store's and the history's included, is measured in the end-to-end test, and what to do about it is decided from that measurement.
- [A pull request's commits and runs use up the report's call budget, or the requests per hour that `GITHUB_TOKEN` can make in the repository] → The report keeps to its call budget, so that one report cannot use up a limit that the repository's other workflows share. When the budget runs out while it reads runs and jobs, the comment marks the CI cost as incomplete, and when it runs out before the report can tell which pull request the push merged, no comment is posted and the job summary says why.
- [A workflow merges a pull request with `GITHUB_TOKEN`] → GitHub starts no workflow run for the push that such a merge makes, so the pull request gets no report, and no job summary says why. The README names this case.
- [A person turns capture on during a session, before the step's first run in it] → The step cannot tell when a setting changed between two runs, so that session's interval begins at its start, and the calls that the session made before the opt-in are recorded. The README tells a person to opt in before they start a session. To keep the intervals, a run that finds either switch off still notes that in the store, which it creates in the repository's common git directory where there is none, even for a person who has not opted in; the note never leaves that directory.
- [Two releases of the hook meet one store, as when sessions start in two worktrees that hold different releases] → The store carries the version of its format, and a run of a release that does not know that version leaves the store alone and records nothing, so the calls of its session are not counted.
- [The hook file in the working tree changes during a session, as when the session checks out a branch that updates the hook] → The registered command that the session read when it started carries the checksum of the hook file that the adopter copied, so it runs none of the changed file, and the session's later runs record, stage, take back and put back nothing. A ledger file staged before the change is taken back by any later run in the repository that finds its command over, and the session's remaining calls are recorded only if the session is resumed once its registration and the hook file agree again.
- [Mutation testing takes time in CI] → Its duration is measured when it is added, and what to do about it is decided then, from that measurement.
