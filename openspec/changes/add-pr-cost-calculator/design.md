# Design

## Context

See `proposal.md` for why. These facts shape the approach:

- Claude Code writes each session's transcript as JSON lines on the machine running the session. Each assistant message carries its model and a `usage` block with input, output, cache-write (split into five-minute and one-hour lifetimes) and cache-read tokens. Current versions also give the service tier, the speed, the inference region and the server-side tool requests, all of which can change the price. One message can be written over several transcript lines. In the main transcripts examined, every line of a message gave its stop reason and the same usage. Subagent transcripts were seen in two shapes. In some, a message's earlier lines gave partial usage and no stop reason, and only its last line gave the final usage and the stop reason. In others, almost no message had a line that gave a stop reason, and every line of such a message lacked fields that final lines carry, among them the server-side tool requests, and gave few output tokens even for a message that called tools: the usage of the call's start, not its end. Claude Code also makes model calls for some of its own tools: the description of its WebFetch tool says that it answers its prompt against the fetched page with a small fast model. Task 1.1 checks which of those calls the transcript holds. Each line names, as its parent, the line before it in the conversation. In the transcripts of one cloud session examined on 2026-11-02, its main transcript and its subagents' transcripts, the line that a call's first line named was often one of Claude Code's own bookkeeping lines, and some of those were written after the call's first line, while the first line that gave a prompt or a tool result up that chain of parents was always in the same file and always written before the call's first line. A tool result's line was written after the output of the `PostToolUse` hooks for its call.
- Each transcript line names Claude's current directory at the time of the call. Claude Code keeps a `cd` from one command to the next only while it stays within the project directory and the directories added to the session, resets it after a command that leaves them, and never keeps one for a subagent. So a call that works elsewhere through absolute paths, with `git -C`, or with a `cd` inside its command, still names the directory Claude was in. The branch a line names was seen reading `HEAD` while a branch was checked out, so it is not used.
- Claude Code runs hooks at set points of a session. `SessionStart` runs when a session starts, is resumed or forked, and when it is cleared or compacted, and Claude Code documents that at a session's start its hooks run in the background while the person can already type, that Claude's first response waits for them to finish, that a prompt sent meanwhile reaches Claude only once they have, that what such a hook prints on standard output becomes context for Claude, and that it cannot block the session. `Stop` runs when the main agent finishes responding, and not when the user interrupts it. `StopFailure` runs instead when a turn ends in an API error. `SubagentStop` runs when a subagent finishes, including the agents Claude Code runs for its own features, and names the subagent's own transcript as `agent_transcript_path`. `SessionEnd` runs when a session ends, as when the person exits or runs `/clear`, and its hooks share a budget of 1.5 seconds, which a hook's own `timeout` raises to match, up to 60 seconds. `PreToolUse` runs before a tool call, with a Bash command's text and the call's `tool_use_id` in its input, and before any permission prompt, and it runs again for a call that a hook deferred when that call is resumed. `PostToolUse` or `PostToolUseFailure` runs after a call that ran, as it succeeded or failed. A tool call refused at a permission prompt or by a permission rule, blocked by another hook, or cancelled while it runs gets neither; Claude Code documents that a blocked call's reason comes back to Claude as the call's error, and that a cancelled call's result carries the interruption message. A command run in the background, or moved there by Claude Code when it reaches its timeout, returns its result before it ends. Claude Code documents that the transcript is written asynchronously and can lag behind the conversation, and that all matching hooks run in parallel.
- A hook on a tool event can carry an `if` condition in permission-rule syntax, such as `Bash(git *)`, which Claude Code checks against each of the commands that a Bash input is made of, those inside `$()` included, and a hook with an `if` condition on any other event never runs. The condition matches a command as Claude wrote it, once leading variable assignments and a fixed list of wrappers, such as `timeout` and `nohup`, are stripped. So git run by its path, through `sh -c`, `env` or an environment runner, or through a shell alias or function does not match it, and Claude Code applies the aliases and functions of the person's shell start-up file to every Bash command. When Claude Code cannot tell which commands an input runs, it runs the hook anyway.
- Every hook receives the transcript's path and Claude's current directory, as `cwd`. A command hook runs in that directory, with two exceptions: in a worktree session started from the desktop app it runs in the main worktree's root, and when that directory no longer exists it runs from the first that still exists of the session's start directory, the project root, the home directory and the temp directory. `CLAUDE_PROJECT_DIR` names the project root, and stays there when Claude changes directory or enters a worktree. Claude Code creates its worktrees under `.claude/worktrees/` in the repository's folder. A hook's command runs in `sh`, in Git Bash on Windows, or, on Windows without Git Bash, in PowerShell, for which Claude Code rewrites `${CLAUDE_PROJECT_DIR}` into PowerShell's own form.
- What a hook's exit code and output do, as Claude Code documents them: Claude never sees the standard error of a hook that exits 0. A `PreToolUse` hook that exits 2 blocks the tool call. A `Stop` or `SubagentStop` hook that exits 2 sends Claude back to work with the hook's standard error as the reason, unless its standard output is empty and its standard error says that a file is missing, which Claude Code treats as a non-blocking error. JSON printed on standard output can block or approve whatever the exit code, except that an exit of 2 blocks whatever the JSON says. Python exits 2 when it cannot open its script, and says that the file is missing or that permission is denied. A command hook's default timeout is 600 seconds, and a timed-out `PreToolUse` hook does not block the tool call.
- A repository's `.claude/settings.json` can set environment variables for everyone who works in it, and they reach every process Claude Code starts, its hooks included, and so can a `.claude/settings.local.json` that the repository tracks, which Claude Code applies over it and reads hooks from too. Claude Code ignores some variables from project settings, among them `HOME` and the `XDG_*` variables. Git reads its global configuration from the file that `GIT_CONFIG_GLOBAL` names when it is set, and `GIT_CONFIG_COUNT` with its companion variables adds settings.
- The checksum that the registered command carries (decision 1) relies on Claude Code keeping, for the rest of a session, the hook registrations that it read when the session started, so that a branch checked out during the session, which can change `.claude/settings.json` as well as the hook file, cannot change the command that a hook runs. Task 1.1 checks that Claude Code does so.
- On Windows, a program started by a name with no folder in it, such as `git`, is looked for first in the folder that the starting program was loaded from and in its current directory, and only then in the system's folders and in the folders that `PATH` names, as the documentation of `CreateProcess` says. Python's `os.path.expanduser` takes the home folder there from `USERPROFILE` and ignores `HOME`, as Python 3.11 was seen to do, while git takes it from `HOME`, and only when `HOME` is not set from `HOMEDRIVE` and `HOMEPATH`, or from `USERPROFILE`.
- In a partial clone, git fetches from the remote an object that a command needs and the clone lacks. With git 2.43.0 as Ubuntu 24.04 packages it, `1:2.43.0-1ubuntu7.3`, whose changelog lists a security patch for CVE-2024-32465 that disables lazy fetching by default in `builtin/upload-pack.c` and `promisor-remote.c`, `git cat-file -s` on a ledger blob that a clone made with `--filter=blob:none` lacked fetched it, and with `GIT_NO_LAZY_FETCH=1` the same command exited with 128 and fetched nothing, as seen on 2026-10-28. Git's own source, read on 2026-10-28, names `GIT_NO_LAZY_FETCH` in no file at v2.43.0 to v2.43.3 or at v2.44.0. It reads the variable in `promisor-remote.c` at v2.43.4 and v2.44.1, whose release notes say that they merge up the fix for CVE-2024-32465, and in `environment.c` at v2.45.0, through a name that `environment.h` defines, so a plain git 2.43.0 to 2.43.3 or 2.44.0 would not read it (T45). No such build was run.
- A cloud session's machine is disposable, and the transcript is gone after it ends, so usage has to be captured during the session. Reading transcripts after the fact also turned out to be slow at the scale of a long pull request.
- A project's cloud threads load a repository's `CLAUDE.md` files and its rules, but run none of the hooks that its settings register. They load the plugins that the person adds in the project's settings, and a person's terminal sessions signed in with claude.ai load the plugins turned on for their account, among them those that their organization turns on for its members or requires. When two enabled plugins share a name, Claude Code registers the hooks of one of them, the one that the organization's managed settings turn on or else the one that it loads first, which `/plugin` shows in a terminal session, while a cloud session has no `/plugin`. A plugin that Claude Code copies into its cache gets the copy's folder as `CLAUDE_PLUGIN_ROOT`, and one that it loads in place, as with `--plugin-dir`, from a skills folder or from a marketplace added by a local path, gets its source folder. Besides hooks, a plugin's manifest can declare MCP servers, monitors and plugins that it depends on, and files in their default places, such as `.mcp.json`, declare components too; a hooks file can hold HTTP hooks as well as commands; and a marketplace's entry for a plugin can add commands, agents and skills to it, its hooks replacing the manifest's for the same event, while `"strict": false` beside any of those stops the plugin loading and `"defaultEnabled": false` starts it turned off. A timeout that a plugin's hook sets does not raise the 1.5 seconds that `SessionEnd` hooks share. A project's thread starts in a folder that holds each of its clones and is in no repository, and many of its calls, its subagents' among them, name that folder. A test plugin on 2026-11-09 saw its hooks run in such threads, with the condition `Bash(git *)` holding, and its start runs come before the first prompt's line, but what one test saw is not a check, so A69 and A70 record those facts as not yet checked, until task 7.2 checks them. A thread's machine pauses between turns and resumes with its files, and one that cannot be resumed continues from a fresh clone. A cloud environment's setup script runs as root before Claude Code starts, and what it writes is the starting point of the environment's later sessions, so a line there can set a session's global git configuration. It does not run again when a paused machine is restored, so a change to it reaches a session that is running only once its machine is rebuilt, while a change to the environment's variables reaches the session at its next restore. An Owner of a Team or Enterprise organization can share an environment with every member and choose the organization's default environment, which a member who has picked none uses, and the organization's managed settings run their hooks in members' sessions, terminal and cloud alike; Projects are not offered on those plans yet. On claude.ai a person adds a plugin by uploading a zip or by adding a GitHub repository as a marketplace, whose new versions reach their account when they check for updates, or by themselves once they turn on syncing, with nothing to accept once a version has synced. Task 7.2 checks in a project's thread what Claude Code's documentation does not say.
- GitHub's jobs API gives each job's start and end times with the default `GITHUB_TOKEN` and `actions: read`. It lists only the latest attempt of each job unless asked for all of them, and a job that has not finished has no end time. Its per-run "billable" timing figure was seen returning zero, so minutes are computed from job times.
- A squash merge puts one new commit on the default branch, and GitHub's rebase merge always makes new commits, so neither brings to the default branch the commits that CI ran on. A pull request's head stays readable from git as `refs/pull/<number>/head`.
- A reusable workflow receives its caller's `github` context, including the event that triggered the caller. The `job` context names the reusable workflow's own repository and commit. Events caused by `GITHUB_TOKEN`, such as a merge a workflow makes, start no new workflow run.
- GitHub's "List pull requests associated with a commit" lists, for a commit that the default branch holds, the merged pull request that introduced it, as GitHub's API description says, and for any other commit the merged and open pull requests associated with it. The report's rule for which push gets a comment rests on that description (decision 7). GitHub's rate limit for `GITHUB_TOKEN` is 1,000 requests per hour per repository, so the report's calls draw on a limit that the repository's other workflows share. GitHub's listing of a repository's workflow runs returns at most 1,000 runs when it is filtered, as by event, by creation time or by commit. `actions/checkout` fetches one commit unless it is asked for more.
- Anthropic's pricing has modifiers beyond the four token rates: higher rates for long prompts on some models, a multiplier for US-only inference, premium rates for fast mode, and a charge per web search. Web fetches cost nothing beyond their tokens.

## Goals / Non-Goals

**Goals:**

- Capture with no service outside GitHub and the repository itself.
- Keep everything a public repository can publish: counts, prices and totals, never content.
- Publish a person's usage only with that person's consent, which holds for each call and not only for the run that records it, and only the calls their sessions make from the repository that publishes it, leaving out any call that capture cannot show was made with that consent or from that repository.
- Keep on the person's machine only what capture needs to tell a call's worktree and branch, to record it once and to take back a ledger file, for no longer than it needs it, readable by that person alone, and no copy of a transcript.
- Make every number in a report reproducible from the ledger, the price table and the jobs API.
- Treat everything that crosses into the tool as untrusted: transcripts, ledger files, API data, and the pull request being reported. `docs/threat-model.md` lists the threats and what answers each.

**Non-Goals:**

- Billing reconciliation. The figure is an API-equivalent estimate, and plans, discounts and included minutes are not modelled.
- Agents other than Claude Code in this change. The ledger format is documented so they can be added later.
- The cost of AI review on the pull request by an app or a job in CI, in the tokens that the app or the job spends. A review that the agent runs in its own session is recorded like its other calls.
- Live cost while a pull request is open. The report runs at merge.
- Reprocessing transcripts, or keeping them as evidence. A pull request's cost is recomputed from its ledger, the price table and the jobs API alone, so the tool keeps no transcript; a capability that keeps transcripts or reprocesses them needs a change of its own, with its own spec, its own threat review and the owner's authorization (DR-178).
- Records that hide whose they are. An entry's call id is a hash, but the commit that adds its ledger file names its author, and where a cloud session commits under Claude Code's own name, the pushes and the pull request that carry it are the person's, and whoever holds the transcript can match the hash to its call, so the ledger is published as the record of the person whose session it holds (decision 16).
- GitHub Enterprise Server, which lacks the `job` context values that decision 7 relies on.
- Repository and CI services other than GitHub, such as GitLab or Gitea.
- Shell commands sent through Claude Code's PowerShell tool, which is on by default on Windows for claude.ai and Console accounts, always on there without Git Bash, and can be turned on elsewhere. A hook registered for Bash never runs for those commands, so capture stages nothing for a commit made through that tool and does not see a change of branch made through it. The hooks that run whatever tool Claude uses, when a turn, a subagent or a session ends, still run on Windows without Git Bash, in PowerShell, so the registered command is written to exit with success there too (DR-031).
- A mode in which an organization turns capture on for its members and they cannot turn it off, and capture that tries to stop a person who avoids it on purpose. Capture is for people who opt in, and the README says how it works and where it stops (task 4.4). Nothing in this change rules such a mode out, since the ledger and the store state their versions, and the rule that capture needs an opt-in that the person, or the environment that they use, sets is held by decision records that a later change can close (DR-189). An organization can already put the opt-in in a shared environment's setup script, or in the environment that it makes its members' default, and its managed settings can write it in their sessions, terminal and cloud alike, so the README tells members how to see what turns their capture on (decision 6).

## Decisions

### 1. Capture with Claude Code hooks, into the git common directory, then into the agent's own commits

*Records:* DR-008, DR-010, DR-011, DR-012, DR-013, DR-014, DR-022, DR-030, DR-031, DR-032, DR-033, DR-034, DR-035, DR-036, DR-052, DR-053, DR-054, DR-055, DR-057, DR-060, DR-125, DR-127, DR-128, DR-129, DR-130, DR-135, DR-136, DR-138, DR-172, DR-184, DR-187, DR-188, DR-199 and DR-211.

One script is registered for eight hook events: `SessionStart`, `Stop`, `SubagentStop`, `StopFailure` and `SessionEnd`, and `PreToolUse`, `PostToolUse` and `PostToolUseFailure` for Bash commands, with the condition `Bash(git *)`, so that around Bash commands it starts for those that run git as Claude writes it, and for any whose commands Claude Code cannot tell (see Context). The run at `SessionStart`, a start run, reads no transcript, since Claude's first response waits for it (see Context), and writes nothing to standard output, which Claude Code gives Claude as context: it takes back and puts back what is due and, when it finds both switches on, begins the session's interval when both were on (decision 6).

For a run of the hook file's registration, this repository is the one that holds `CLAUDE_PROJECT_DIR`, so a run means the same repository whatever directory Claude has moved to, while a run of the plugin works on each repository that it meets, as decision 17 says, and in each does what this decision says of this repository. Every run but a start run, whether a turn, a subagent, a failed turn or the session has ended or a git command is about to run or has run, reads the session's transcript on from where it last stopped, reading again the lines that a call not yet recorded may still answer (decision 6), and the subagents' own transcripts, which Claude Code keeps in a `subagents/` folder nested under the session's. It keeps each call whose line gives a working directory in this repository: one whose git common directory, as git finds it from that directory when the run reads the call, without the session's `GIT_` variables (below), is this repository's, so that the repository's worktrees count and a separate repository nested in its folder does not. That directory alone tells a call's repository and worktree, never what the call reads or writes, nor the branch. A call whose line gives no working directory, or whose directory no longer exists, as when a worktree is removed before a run reads its calls, or names no repository that git can tell, is left out. When the line gives no directory, or that directory is inside this repository's folder, where Claude Code keeps its worktrees, or holds this repository's folder, as a project's cloud thread's folder holds its clones (DR-199), the session's next ledger file here says that calls whose repository could not be told were left out, with no count (decision 16); when it is outside, nothing here says so, so that no ledger file tells of work in another folder. A clone that git does not trust, as one that another user owns and that no `safe.directory` setting names in the person's global configuration or the system's, the only files that git takes it from once the session's `GIT_` variables are removed, holds no repository that git can tell, so a run there records, stages and takes back nothing, and the README will name `safe.directory` for such a clone, and where to set it (task 4.4). Of those, it records only the calls made while both switches were on (decision 6). It records each such call in a store inside the repository's git common directory (`git rev-parse --git-common-dir`), outside the working tree and shared by every worktree, together with the worktree that git itself finds from the directory the call's line names, which for a directory inside a worktree under the repository's folder, as Claude Code's are, is that worktree and not the main worktree around it, and which the store knows by the worktree's folder in the git common directory, which `git worktree move` keeps, or as the main worktree, which has no such folder and which `git worktree move` does not move, and the branch checked out there when the call is recorded, or the fact that none was. Because a run comes before every Bash command that the condition matches, a call that the transcript holds as over by then is recorded before that command can change its branch, unless that run reaches its time budget before it reads the call. Apart from staging a ledger file, taking it back and putting it back, as below, it changes nothing in the working tree or the index, so recording never blocks a change of branch or a rebase.

A call's usage is read from its lines that give a stop reason. Where none does, as in one shape of subagent transcript, the call is read from its last line once it is over: once a later call follows it in the same transcript, or once its agent has stopped, which `Stop`, `StopFailure` and `SubagentStop` say. The ledger counts the calls read that way, because their lines give the usage of the call's start, and the comment gives that count and says that the token cost is then a lower bound. A call that is not over yet waits for a later run. A call whose usage holds a field that the script does not know, at its top level or in a block nested in it, is recorded from the fields that the script knows, and the ledger counts such calls without naming the field, because a new field can carry a charge that the entry then leaves out, so the comment gives that count and says that the token cost may then be low. A run reads only the lines that end in a line break, because Claude Code can still be writing the last one, and a line that a run began with, or began as the first line that no earlier run read whole, and could not finish reading within its time budget is skipped by the next run and counted as one refused call, so that no one line, however long, holds capture back for good.

Before a Bash command that runs `git commit` in this repository, the script first reads the transcripts as above. A command runs `git commit` when one of the commands it is made of, split as the shell splits it, is `git`, then any of git's own options, then `commit`, and is not a dry run, which it is when any of `--dry-run`, `--short`, `--porcelain`, `--long`, `-z` and `--null` is in effect once git has read the commit's options, in any spelling that git accepts, such as `--dry` or `-qz`. For git, `--short`, `--porcelain` and `--long` are one setting, which the `--no-` form of any of them clears, so `git commit --porcelain --no-short` makes a commit. A `PreToolUse` run comes before the whole command, so it cannot see what an earlier part of the command will stage, nor which branch a commit after an arbitrary command lands on, nor when a commit in the background will run. So the script stages a ledger file only when the commit is a top-level command, joined to the rest by `&&`, `;` or line breaks and not part of a pipeline, whose other commands run beside it, runs in the foreground, which a commit followed by `&` does not, and comes after nothing but `cd` to a path written in the command and the git commands `add`, `rm`, `mv`, `status`, `diff`, `log` and `show`, with or without git's own options, which are what an agent runs before a commit and which do not change the branch themselves. A command substitution or a process substitution runs before the commit, or beside it, wherever it is in the commit or in a command before it: in an argument, in a leading assignment, or in a redirection. So each counts as a command that comes before the commit, except one whose only command is `cat` reading a here-document whose delimiter is quoted, which is one way to pass a message of several lines, and in whose body the shell expands nothing. The shell runs any command substitution in the body of a here-document whose delimiter is not quoted, so when the commit or a command before it reads one, the script stages nothing. For any other command it stages nothing, and the calls wait for a later commit. The worktree where the commit runs is the hook input's `cwd`, followed through each top-level `cd` before the commit and the `-C` options given to git before `commit` in the commit's own command, never the directory the hook runs in, which in a desktop worktree session is the main worktree (see Context), and the script stages nothing when such a `-C` option names a path that is not written in the command. A `-C` given to an earlier git command does not move the commit, and a `-C` after `commit` names a commit whose message the commit reuses.

When it stages, the script writes the calls recorded for that worktree and the branch now checked out there, which no ledger file on that branch holds and which the store has not noted as taken, into one new file, `.pr-cost/ledger/<YYYY-MM>/<random>.jsonl`, created only if no file of that name exists, and stages that file alone, with `--force` so that an ignore rule cannot drop it, and `--sparse` so that a sparse checkout that leaves out `.pr-cost/` cannot refuse it. It writes nothing when no call is waiting; when the command names the paths to commit, which leaves the rest of the index out; when the commit would commit nothing without the file, counting the changes to tracked files that `-a` adds, and no `git add`, `git rm` or `git mv` comes before it, so a commit that would fail still fails, and an empty commit asked for stays empty; when a `git rm` or `git mv` before the commit is given a `-C` path not written in the command, or names a path with a wildcard or other pathspec magic, a path not written in the command, or the folder that the file goes in or one above it, read from where that command runs, after the `cd`s before it and its own `-C` options, because `git rm` refuses to remove a newly staged file and fails the command, and `git mv` moves it where the script does not look for it; and when `git check-attr`, which reads every attribute file that git does, the repository's `.git/info/attributes` and the person's own among them, gives the ledger path a `filter` or a `working-tree-encoding`, because git can then commit a pointer, as Git LFS does, or the file decoded from another encoding, instead of the entries. When git refuses to add the file, as it does where `core.safecrlf` is on and line endings are converted, the script removes the file it wrote and stages nothing. When a `git add` does come first and stages nothing, the commit holds the ledger file alone instead of failing, which is a residual.

After the command, its `PostToolUse` or `PostToolUseFailure` run checks whether the commit now checked out in that worktree holds the file. If not, that run takes the file back, from the index and the working tree, and its calls wait for a later commit. Once any run finds a commit holding a file that the script staged, the store notes the file's calls as taken, and the script never stages them again in that run's clone, so that in that clone a ledger file that someone removes from the branch later, in whatever way, takes its calls with it, even when the changes of its commit are committed again. From then on the script leaves the file to git, like any file that a commit took, and never takes it back: a removal that leaves it in the working tree, untracked or with only the intent-to-add index entry that `git reset -N` leaves, as a mixed `git reset` or a `git rm --cached` and a commit do, leaves it where a later `git add -A`, or for an intent-to-add index entry a `git commit -a`, commits it again, with its calls, on whatever branch is checked out then, as they commit the other changes that a reset leaves, unless a sparse checkout leaves it out, or an ignore rule matches it while it is untracked. So a squash made with a mixed `git reset` and `git add -A` keeps the ledger files of the commits it squashes, and their calls, except in the cases that the risks name. A command that was refused or blocked, and so never ran, or that was cancelled or interrupted, gets no such run, and an interrupt runs no `Stop` either. So the store notes, for each staged file, a hash of the session's id, the path of its transcript, which every run of that session brings up to date because Claude Code moves a session's transcript when the session enters or leaves a worktree, and a hash of the `tool_use_id` of the command the file was staged for, until a run resolves the file (decision 15). Any later run of the step in the repository, from that session or another, takes the file back once it finds that command over: by the command's result in the transcript, by a later call of the agent that ran it, by that agent having stopped, or by its session having ended, which `SessionEnd` says. A run takes back and puts back what it can before it reads any transcript, as a session-end run can for every file staged for its session's commands, so that a long transcript does not use up its time first. A `PreToolUse` run that fires again for the same `tool_use_id`, as for a deferred call when it is resumed, stages nothing new while that command's file is still staged and the branch it was staged for is still checked out in that worktree. When that branch is no longer checked out there, it takes the file back first, and then, as when a run has taken the file back meanwhile, it stages anew. A take-back never removes a file from a worktree whose checked-out commit holds it, and leaves the file while another git command holds that worktree's index lock, rather than waiting for the lock or removing it. A plain `git commit` holds no index lock once it has read the index, while its `prepare-commit-msg` and `commit-msg` hooks run, so a take-back can remove the file from the index after the commit has taken it, as when Claude Code moves a commit to the background at its timeout and returns its result early. A reset in the commit's own command, as in `git commit && git reset HEAD~1`, leaves the file where that command's run takes it back, too, while a later `git reset` can go back to that commit. So every take-back notes the commit that it found checked out there, not holding the file, and whether it removed the file from the index, the working tree or both, and the first later run that finds another commit checked out in that worktree and the index free puts the file back, as that commit holds it, if that commit holds it: into the index, if the take-back removed it from there and the index lacks it, and then into the working tree, if the take-back removed it from there, the index holds it as that commit does and the working tree lacks it, before the agent's next git command could commit its deletion. Then it forgets the note, whether it put the file back or not, so that a ledger file that the person removes later, or that the step never took back, is never put back. The script puts nothing back in any other case, so that a removal that the index holds stands, as after a `git reset --soft` back to a commit that holds the file, unless it comes while a put-back into the index is due, as the risks say. ### 15. The store keeps only what capture needs, for as long as it needs it

*Records:* DR-173, DR-174, DR-175, DR-176, DR-177 and DR-178.

The owner allowed the store to keep, on the person's machine, the worktree and the branch of a call, a session's id, a transcript's path and a `tool_use_id`, only where capture needs them to tell a call's worktree and branch, to record it once, to take back the ledger file of an interrupted command or to clean up safely, and never to publish them. So the store is one file for each user, in a folder of that user's own directly in the git common directory, `pr-cost-<uid>/store.json` where the system numbers users, as POSIX systems do, and `pr-cost/store.json` where it does not, so that no folder of the tool's is shared between users, written whole (decision 1), and holds, field by field:

- `version`: its format's version, so that a release that does not know it leaves the store alone, and a later one upgrades it (DR-187).
- `fingerprint`: a hash of the fingerprint that the last run that found both switches on noted, whichever session it ran for, which the next such run compares with its own (decision 6).
- `sessions`: one entry per session, keyed by a SHA-256 hash of the session's id, never the id itself, holding its intervals, each with the times of the run that began it and of its last run and whether it has ended (decision 6); for each transcript that its runs read, keyed by a hash of its path, how far runs read it, where the earliest line that a call not yet recorded may still answer begins and where a line too long for a run's time budget began, so that a call is placed by the line it answers, no call is recorded twice and no one line holds capture back; whether a run left out its calls because their repository could not be told, which its next ledger file here says (decision 16); the latest time that its runs noted or that a line they read gave, so that a clock moved back is seen (decision 6); the latest release whose copy of the capture step has run in it, so that an earlier release's copy leaves the session to the later one, but for an opt-out (decision 1); and the time of its last run, for the retention window.
- `waiting`: each recorded call's entry, as its ledger file will hold it, with hashes of its session, of the worktree that git finds from its line's working directory, by that worktree's folder in the git common directory, and of the branch checked out there when it was recorded, or the fact that none was, so that it goes only to a commit in its worktree, on its branch (DR-012).
- `flags`: each flag due for calls left out for consent or for their age, with the same three hashes and the day a run last raised it, so that the next ledger file staged for that worktree and branch says so, and no other does (decision 16), and the retention window drops it.
- `taken`: the hash of each call whose ledger file a commit took, with the call's day, so that it is never staged again in that clone (DR-055).
- `staged`: for each ledger file that a run staged and no run has resolved, the file's path in the worktree, the worktree's name, which is its folder in the git common directory and leads git to it, or the fact that it is the main worktree, the hash of the branch it was staged for, the session's hash, the transcript's path, a hash of the command's `tool_use_id`, the flags it carries and the calls it holds, so that a later run can tell that the command is over, take the file back and return its calls and flags to `waiting` and `flags` (DR-014).
- `taken_back`: for each take-back, the file's path, the worktree's name, the commit found checked out and what it removed, until the run that puts it back or forgets it (DR-130).

A hash is the SHA-256 of the value alone, since equality is all that a run needs of a session's id, a transcript's path, a worktree, a branch or a `tool_use_id`, and it is not anonymity: whoever holds the value can compute it, so none of them, plain or hashed, reaches a ledger file. Beside the ledger file's own path, the only plain names that the store holds are the worktree's name in `staged` and `taken_back`, which git takes from the name of the worktree's folder, and the transcript's path in `staged`, because a take-back has to run git in that worktree, which git's folder of that name leads to, and read that transcript; they go when their note does. That path carries the session's id and the person's home folder, so while a ledger file is staged the store holds the session's id in plain there, as the README will say. The store holds no line of a transcript and no value from one beyond an entry's fields and these notes, and nothing of a transcript goes into any other file, so that no transcript is kept for reprocessing (DR-178).

Retention, over a window of 30 days, which the owner picked on 2026-11-03 from 7, 14 and 30: a run records no call whose day is more than 30 days before the run's day, and drops a waiting call, a flag due or a taken call's note that old, a flag by the day a run last raised it, flagging a dropped waiting call for its age in the next ledger file staged for its worktree and branch, so that the store never holds a call that it may still record without its note; a session's notes go once none of its runs has come within those 30 days; a staged file's note that old is taken back as for a command that is over, and a take-back's note that old is dropped. A run that leaves the store holding nothing, no flag among it, removes its file and its folder. Every run that finds a store of a version that it knows applies the window and removes an empty one, whatever the switches say (decision 6), and one that finds a version that it does not know leaves the store as it was (decision 1). Retention runs only when a run comes, so a repository where no session runs again keeps its store until the person removes it, which the README says how to do.

Protection: each write leaves the folder with mode 0700 and the file with 0600, whatever the umask or the modes it found. A run writes the new store to a new file that it creates itself, never through a link, syncs it to disk and renames it over the old one, and removes a new file that a killed run left. Where the system numbers users, a run opens the store's folder once, without following a link, checks the folder's owner and kind on what it opened, and creates, writes, renames and removes the store's files only through that opened folder, so that a folder that someone replaces with a link between the check and the write redirects none of them (T112). It leaves alone a store whose file or folder is a link or, on Windows, another reparse point, which Python's `st_file_attributes` shows, is not a regular file or a folder, or, where the system numbers users, is not owned by the user it runs as, as it leaves alone a store whose version it does not know, and it opens a transcript only when it is a regular file. A run that cannot create or enter its own folder records, stages, takes back and puts back nothing, says so on standard error in its own words, and exits with success. A note's paths are acted on only for a file of the form that the step writes, in the ledger folder of a worktree whose git common directory is this repository's, and a run checks each waiting call's entry again when it stages it, by the rules that it records by, so that an entry that someone wrote into the store carries nothing into a ledger file. On Windows, where a file's mode sets only its read-only flag, the step checks neither the store's access list nor its owner, so there the store can have the access of the git common directory around it, as the README says.

A store that the person, or anything else, removes, or that does not parse, as when a sync or a power loss cut it short, takes its notes with it: the next run that finds both switches on begins a new interval, so that no call that answers a line written before that run is recorded, however far the transcripts were read, and a ledger file staged before the removal is left to git, since no note says that a run staged it, so the README says to look for one with `git status`, in every worktree that `git worktree list` names, before removing the store. A run that finds a switch off removes a store that does not parse, as it removes an empty one, so that a broken store does not stay. A store does not parse only when a run cannot read a version from it, or reads one that it knows from a store that is not of that version's form: every version of the store is a JSON object whose `version` field every release reads in the same way, so that a run tells a store that a later release wrote, which it leaves alone (decision 1), from a broken one, and a run looks for a version only in a store that the protection above does not leave alone (DR-187). A fresh clone at the same path holds no store, so a session resumed there stages none of the calls that answer a line written before its first run there, those of a ledger file that its branch no longer holds among them (DR-184). A copy of the store that a backup or a sync puts back after an opt-out brings back no call when the opt-out changed a file that the fingerprint holds, since the run that notes another fingerprint does what an opt-out does, as the risks say.

## Risks / Trade-offs

- [Claude Code changes its transcript format] → The parser keeps to the fields it needs, refuses unknown shapes with a count instead of guessing, and its fixtures carry every shape seen in each kind of transcript, so a change shows up as a failing test. A call whose two final lines disagree, or whose usage block gives a cache-write split that disagrees with its total, is refused. A usage field that the parser does not know is not a reason to refuse the call, whose known fields still price it, but the ledger counts such calls, and when there are any, the comment gives their number and says that the token cost may be low, because the new field can carry a charge that the entry leaves out.
- [Claude Code makes model calls for its own tools, such as WebFetch, that the session's transcript does not hold] → Those calls are not counted. Task 1.1 checks which of Claude Code's own model calls the transcript holds, and the comment and the README say that the calls it does not hold are not counted.
- [A call read without a stop reason gives the usage of its start, not of its end] → Its output tokens and server-side tool requests are too low. The ledger counts such calls, and when there are any, the comment gives their number and says that the token cost is a lower bound.
- [Some calls reach no commit] → A call waits for a `git commit` that capture stages for, made in the worktree and on the branch where the call was recorded. So these calls are not in any pull request's ledger:
  - calls made after the agent's last such commit on a branch, such as pushing and opening the pull request, and the call that runs that commit, if that commit's run cannot yet read it as over, as it never can in a subagent transcript whose lines give no stop reason, and as it cannot when the transcript lags behind, and any call that that commit's run leaves unread at its time budget;
  - calls recorded on a branch that gets no later commit, such as the default branch before the agent branches off, or in a worktree where nobody commits, or one that Claude Code removes when a subagent finishes without changes;
  - calls recorded while no branch is checked out, as during a rebase that stops at a conflict, unless a commit is made the same way.

  Calls also wait, and may reach no commit, when the agent commits in a way that capture does not stage for: `git merge`, `git cherry-pick` or `git rebase --continue`, a script, a commit made through an API or through Claude Code's PowerShell tool, a commit in the background, in a pipeline, in a subshell or a group, joined to another command by `||`, or behind a wrapper such as `timeout`, one that follows another command in the same input, one whose message another command writes or a here-document whose delimiter is not quoted holds, or one made by git written in a form that the hook's condition does not match, as Context lists them. They wait too while a repository's own git hook refuses the ledger file, and in a repository whose attributes give the ledger path a filter or a working-tree encoding, or where git refuses to add the file, no call reaches a commit. The comment counts the usage that the pull request's commits carry, and the README says so and names these cases.
- [A call is recorded on the branch checked out when it is recorded, which can differ from the one it was made on] → A run before every Bash command that the hook's condition matches narrows this to three cases. One is the call that runs a command that changes the branch, when that command's run cannot yet read it as over. Another is any call that that command's run leaves unread at its time budget. The third is calls followed by a change of branch that no command the condition matches makes: one that a script or the person makes, one made through Claude Code's PowerShell tool, or one made by git written in a form that the condition does not match, such as by its path, through `sh -c`, `env` or an environment runner, or through a shell alias or function. Those calls go to the branch checked out next. A command that the script stages for can also run a program that git's own options or environment variables in that command name, such as `git -c diff.external=<program> diff`, `git -c core.hooksPath=<folder> commit` or `GIT_EDITOR=<program> git commit`, and a change of branch that such a program makes before the commit takes the staged ledger file, with its calls, to the other branch. The owner kept this rule on 2026-11-02, rather than leaving a call out when a change of branch comes between its making and the run that records it.
- [A git add that stages nothing comes before a commit that would otherwise commit nothing] → The commit holds the ledger file alone, where it would have failed without the tool, because the `PreToolUse` run cannot tell what the `git add` will stage.
- [A commit is refused at a permission prompt or by a permission rule, blocked, cancelled or interrupted after its ledger file was staged] → No run follows that command, so the file stays staged until a run of the step finds the command over and takes the file back: the session's next git command, turn end or end, or another session's next run in the repository. Until then, a git command finds the file staged, whether the person runs it outside the session or the agent runs it before the transcript shows the command's result: `git rebase` refuses to run, `git checkout` carries the file to another branch, where a commit takes it with its calls, and `git stash` takes it. A session whose process is killed during its commit, before the command's result is written, leaves the file staged until the person removes it or the session is resumed. A call that another hook defers leaves it staged until the call is resumed, unless a session-end run takes it back when the deferral ends the process, which Claude Code's documentation leaves open; either way the resumed commit carries the calls, in the file still staged or in a new one, unless that branch is no longer checked out by then, when the resumed run takes the file back first and the calls wait for their own branch, or, when that run finds the index lock held, leaves the file staged, and a commit that starts once the lock is free takes it, with its calls, to the other branch.
- [A git command starts while a run stages or takes back a ledger file] → It fails at the index lock, as when any two git commands meet in one worktree. A run holds the lock only for the one file it stages or takes back, and a take-back that finds the lock held leaves the file for a later run, rather than waiting or removing the lock. - [The published schema and the report disagree about a line] → The ledger format lists what no schema can hold, where the report's rules decide; the schemas use ASCII patterns rather than `format`; a property-based test compares the schema with the reader; and a released version's schema is held by its hash, so a third party's check disagrees with the report only where the format says it may.
- [The hook file in the working tree changes during a session, as when the session checks out a branch that updates the hook] → The registered command that the session read when it started carries the checksum of the hook file that the adopter copied, so it runs none of the changed file, and at the session's later hook events the capture step does not run, so it records, stages, takes back and puts back nothing. A ledger file staged before the change is taken back by any later run in the repository that finds its command over, and the session's remaining calls are recorded only if the session is resumed once its registration and the hook file agree again.

- [Mutation testing takes time in CI] → Its duration is measured when it is added, and what to do about it is decided then, from that measurement.
- [A rewording changes what a requirement, a scenario, `CLAUDE.md`, a threat's answer or an instruction to adopters says] → Task 1.20 replaces the glossary's words to avoid, and fixes the uses of a word with several senses, without changing what any text requires; a title that changes, changes with the register, the cross-references that quote it and the threat model's citations, and a title that an accepted record quotes keeps its words.
